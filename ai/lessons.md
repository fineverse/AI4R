# 教训档案（lessons）

> **用途（2026-10-01 第七十八轮立）**：收纳散落在 `ai/rules.md` / `ai/workflows.md` 各节里的**起因、事故与历史演化叙事**——它们解释"规则为什么长这样"，但对**执行规则本身无用**；拆出来后，两个规则文件只留可执行指令 + 一行指针到这里。**新教训产生时：规则进规则文件、叙事进本文件，两边各写各的。**
> 每条尽量给出原始记录指针（rounds 卷 / 原出处节）。

## 一、覆盖与丢失（本工作空间最痛的一类）

1. **rounds-57 覆盖事故（2026-09-30，支线协作纪律的起因）**：并行会话里支线按"主线程模式"写了轮次记录，**覆盖了主线程正在写的 `rounds-57.md`**；另一次还误删了 `rounds-55.md`（均从 git 恢复）。根因：没有一处声明"谁在改哪些文件"，支线动手前既没读 `CURRENT.md` 也没看 `git log`。→ 由此定下双通道同步机制与"支线只投递"。
2. **脚本拆分静默丢失（2026-09-23，清理纪律第 8 条的起因）**：一次脚本拆分因运算符优先级 bug（`A if cond else B + C` 被解析为 `A if cond else (B + C)`）导致两个文件的后半部分（59 KB + 24 KB）**静默丢失**——当时工作空间尚未 git、无备份，只能从轮次记录重建（事实与 `文件:行号` 完整，措辞无法还原）。→ 教训：**脚本拆分必须自证（体积守恒 + 死链检查），不能只看"命令跑成功了"**；也是"轮次记录与 judgments 必须保持可重建密度"这条安全网的由来。
3. **"删除有闸、覆盖无闸"实测（2026-09-30，沙箱边界投递）**：`rm` 走命令审批（弹窗），而**写文件不弹窗**——支线一轮内写了上百个文件（含 `tools.md`、`check_links.py` 等既有文件），全程未触发一次询问。⇒ 搞丢成果的真实路径是**覆盖**不是删除，版本控制 + 异地副本是唯一解。**沙箱可写区**实测形状：工作空间 + `/tmp` + `~/.cache` 等包缓存（**注意区分**：沙箱可写 ≠ 权限模式自动允许——后者只含工作空间，故访问 `/tmp` 仍会弹授权，见 §二.4）；家目录根、`~/dev`、`~/.config`、`/etc` 一律拒绝。

## 二、权限与弹窗（临时根的演化）

4. **第四十八轮重大修正**：最初为减少授权弹窗，把中间产物集中到工作空间外的 `/tmp/ai4r/`——**这个选择本身就是弹窗主因**（权限自动允许范围是工作空间，`/tmp` 在外面，每次读写都走授权；纪律在制度性地制造弹窗）。用户两次反馈后改为：**临时根进工作空间 `inbox/scratch/` + `git init`**。→ 教训：想让某个动作"不打扰用户"，先看它落在权限边界的哪一侧。
5. **第 6 条"只读优先"被长期违反**（第四十八轮发现）：违反形态两类——用 Shell 跑 `grep|cut`、`sed -n`、`cat`、`find`、`wc -l`（全是 Read/Grep/Glob 能做的），一轮内约 6–7 次；加 `dangerouslyDisableSandbox` 测外网（用户当场看到弹窗并打断）。→ 教训：**"写了纪律"不等于"纪律会生效"**，此后按"每次 Shell 调用都要能说出为什么不能用专用工具"执行。
6. **历史路径注记**：第四十八轮前的规则与轮次记录里出现的 `/tmp/ai4r/` 是当时的事实，不追改；`inbox/cleanup.md` §执行记录里有三次 `/tmp` 清理的台账（877 MB → 28 MB → 16 MB + 88 KB）。

## 三、计数与清单漂移（机器检查的由来）

7. **"RL 词义"三处各写一个数（第三十三轮）**：`judgments.md` 同一清单在三条里分别写成 3 / 5 / 9 种、且全是现在时 → 统一为九种 + 指针。→ 「**引用可以重复，计数不能**」的原始出处；后升格为 COUNT_RULES 机器检查（第九项）。
8. **一条判断被静默删（第四十四轮）**：D 组节标题与索引表都写 11 条、实际只有 10 条——第十七轮的一条判断在某轮编辑中被静默删掉。→ 判断条数一致性检查（第八项）的由来。
9. **拆册后引用没跟改册 ×65（第二十八、三十轮）**：C003 的 §I–§P 共 52 处、C005 的 §K–§M 共 13 处。→ 章节可达性检查（第五项）与"分册不是唯一处理"分档政策的由来。
10. **卷数连续两次差 1（第六十七、七十六轮）**：声明"47 卷"实 48、"57 卷"实 58——同一个派生值手写多处、权威源在文件数。→ 卷数并入 COUNT_RULES（第七十六轮）、README 卷数声明并入（第七十八轮）。
11. **"17 条线索级"漂移（第七十七、七十八轮）**：scoring_line §二实际 15 条，四处声明写 17（第四处因加粗分隔逃过 Grep）。→ 教训：**措辞修正后要用多种分隔形态复查**；该计数已入登记表。

## 四、同步与传播（收尾同步位清单的由来）

12. **第 73–75 轮漏 README「最近动态」**：收尾时 README 仍停在"54 卷 / 最新第七十二轮"。→ "同步 7 处"权威清单（第七十七轮）的直接动因。
13. **第 67/68 轮漏指针表行**：漏行不产生死链（卷文件存在、history.md 也链接它），现有检查全抓不到。→ 第 13 项「README 轮次表完整性」（第七十七轮）。
14. **第 55/57/59/60 轮具身侧零记录**：四轮对具身文件有实质改动，`embodied-ai/history.md` 停在 29 轮；embodied state 还把第 59 轮的工作误记到第 55 轮名下。→ "改具身文件 → embodied history 必须含本轮条目"入同步位附注（第七十八轮）。
15. **检查清单三处各写一遍（第六十五轮收敛前）**："十项 / 十一项 / 十二项"在脚本 docstring、`shared/index.md`、`workflows.md` 三处各写一次，加一项要改三处、实际漏过两次（第 62、64 轮）。→ 「清单只在脚本 docstring 枚举」的规定。
16. **第 60 轮投递物虚报**：投递物称某事实"已写进 `tools.md`"，实际没有，且旧文字与新证据相反。→ "投递物里的事实要复核再落盘"（收尾第 9 步）与模板 §三 的写法要求。

## 五、规则演化史（废案与例外）

17. **支线协作三代放宽**：第六十二轮从"全禁"放宽为"可新建、不能修改"；第六十六轮为 `CURRENT.md` 开多写者例外；第六十七轮取消该例外（理由：① 它是机制里唯一被豁免的多写者文件，两条支线同时追加即 last-write-wins，恰是本机制要消灭的风险；② 它只是 `ls inbox/` 的冗余副本，违反单一事实源）。
18. **"为冲突开例外会制造新冲突"**（第六十六/六十七轮的两条同类教训）：修规则时要看新规则会不会与既有规则打架，也要看新机制是不是在重复已有事实。
19. **周扫首跑实测（2026-09-30）**：两张几天前刚建的表里"无代码"标签当天就有 3 条被推翻；§1 的 13 行格局与官方实时榜差到"榜首完全换人"。→ §周扫三线设计与"易失效断言"分类的实证基础。
20. **`check_links` 的"永久报警"宿命**：第 11 项若不归零会永久报红、几轮后被无视——所有不归零的检查都有这个宿命（inbox 豁免、archive 跳过等设计都源于此）。

## 六、写作与引用陷阱

21. **路径层数写少一层 ×2**（第三十三、三十四轮）：卷文件在 `projects/<项目>/history/` 下、比 `state.md` 多一层，引用 `ai/`、`shared/` 要 `../../../`——两次都被 `check_links.py` 当场抓到。
22. **笔记"意义"节 7 种命名变体（第三十一轮）**：对本项目的意义 / 用途 / 与本项目的关系 / 与 DiffusionDrive 的关系 / 迁移到自动驾驶……5 篇还只写成"在脉络"节里的粗体 bullet。→ 统一为 `## 对本项目的意义` + 机器检查（第六项）。
23. **"见上条 / 见下条"随插条变错（第四十三、四十四轮）**：新条目插在既有条目之前，使"见下条"与"见本组"两处同时指错。→ 组内交叉引用要"显式指认"（写清哪条、哪个组）。
24. **"实测 X 轮漏了 Y"的通用教训**：凡是"每次都要记得"类的约定，本工作空间反复证明会失效（第 49–54 轮漏收尾步骤且无警报）——**要么进同步位清单、要么进机器检查，否则等于没写**。
