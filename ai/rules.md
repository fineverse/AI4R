## 证据等级

**本表是工作空间内证据等级的唯一定义处**；`shared/research-workflow.md` 与 `ai/templates.md` 只引用、不重复。区分以下等级，不得混淆：

| 等级 | 含义 | 示例 |
|---|---|---|
| 元数据 | 仅从 DOI/OpenAlex/Crossref 获取标题、作者、年份 | "该论文发表于 IEEE TIV 2024" |
| 摘要 | 已读出版社或 arXiv 摘要 | "摘要声称覆盖 270+ 篇论文" |
| 全文 | 已读完整论文文字 | "论文第三章讨论了评价协议" |
| 代码静态检查 | 已查看仓库代码结构和关键文件，未运行 | "损失函数在 `loss.py:45` 定义" |
| 成功运行 | 已在本地成功运行并产生输出 | "在 NAVSIM v1 上复现了表 2 的 L2 误差" |
| 独立复现 | 从零搭建环境并独立验证 | "独立训练并得到与论文一致的结果" |

不得将低等级证据当作高等级使用。没有代码的论文降低对其实现和结果的信任度。**论文表的证据状态列不得使用词表外档位**（历史漂移实例见 [lessons.md](lessons.md) §六）。**例外**：综述类表（如 [`direction/surveys/e2e_ad_surveys.md`](../projects/autonomous-driving/direction/surveys/e2e_ad_surveys.md)）可用"窄词表"（如 `全文目录` / `项目页`），但须在表头声明该表口径。

### "代码静态检查"必须再分三级

同一个"代码静态检查"标签下，核查强度差别很大，**标注时必须带级别**：

| 级别 | 做法 | 能支持什么结论 | 不能支持什么 |
|---|---|---|---|
| **L1 逐文件核验** | 克隆后读关键文件与配置，逐项对齐 `文件:行号` | "论文声称的机制在代码里是否真的实现" | 性能与延迟 |
| **L2 仓库存在性** | 只确认仓库可访问、README 与目录结构 | "有没有官方代码" | 机制是否实现 |
| **L3 API + `raw` 取证（未克隆）** | 走 GitHub trees API + `raw.githubusercontent.com` 逐文件取内容（**不占 API 额度、不占磁盘**），**逐文件比对字节数与树接口** | 与 L1 同级的机制核验（**用于克隆失败的仓库**） | 需要运行才能知道的量 |

**配套事实（写入 `repositories.md`）**：L3 的字节数必须与 trees API 的 `size` 逐一对齐，否则视为取证不完整。**已知克隆会失败的情形**：大仓（>100 MB）、含 LFS 的仓、tarball 在固定字节处截断。

**与质量分档的关系**：证据等级回答"我读到了什么程度"，**质量分档**回答"这篇值不值得读"。判断预印本（无 venue、无引用）时按 [shared/literature-quality.md](../shared/literature-quality.md) 分档（T1–T5）并标注可复核依据。

**⚠ 撞名消歧**："**L2 级别**"（本表的仓库存在性）与 nuScenes 的 "**L2 误差**"（平均位移指标，见 benchmarks.md §2.8）撞名——前者只在**证据等级**语境、后者只在**指标**语境使用；同一句里两者都出现时必须展开全称。

### venue 核验必须三渠道并行

"取不到 venue"常常不是"没有 venue"，而是 **arXiv `comments` 里没写**。三条渠道：

1. arXiv `comments` 字段（注意区分 "**Submitted to** X" = 投稿 与 "Accepted by X" = 录用）
2. OpenAlex 按标题（**匿名查询会 429 限流，需备用渠道**）
3. Crossref 按 DOI 反查

**按标题在 arXiv 找不到时，先怀疑"根本没有 arXiv 版本"**（会议版 / 已撤稿投稿两类实例见 [lessons.md](lessons.md) §三同类教训）→ 去 OpenReview 与出版社目录页反查。

## 子代理纪律

1. **子代理只出线索，主线程做判断与写回**。子代理返回的是"发现了什么、在哪个位置"，不直接决定工作空间内容。
2. **子代理不得写文档**（用户明确要求）；可以检索、读文件、跑只读命令。
3. **多轮探索与批量信息收集一律委派**：全库搜索、多文件通读、开放式调研交给 Explore 子代理，主线程只保留规划、决策与最终审阅。
4. **主线程自己做**：单次快速查（一次 Glob/Grep/Read），以及**任何将成为交付物内容的部分**（例如要写进文档的原文摘录）。
5. **必须缓存**：子代理取回的外部文件缓存在 `inbox/scratch/<name>_probe/` 供主线程复核——**GitHub 未认证 API 限 60 次/小时**，子代理要省着用（优先 `raw.githubusercontent.com`，它不占额度）。
6. **不克隆大仓**（98–452 MB 级会让工作空间翻倍）→ 改用 L3 的 API + `raw` 取证。
7. **全库 Grep 默认排除 `projects/*/code/repos/`**，避免第三方代码噪声。

## 支线协作纪律

主线程（长驻、按轮次推进）与支线（短命、探索与讨论）并行时的分工与**同步机制**。（起因 = 2026-09-30 的 rounds-57 覆盖事故，完整叙述见 [lessons.md](lessons.md) §一.1。）

### 一、分工（谁改什么）

1. **支线"可以新建、不能修改"**：**目标路径不存在 = 没有任何人在写它 → 零竞争 → 可直接写**；**目标已存在 = 主线程随时可能也在改 → 必须投递**。判定：
   ```bash
   git ls-files --error-unmatch <path> 2>/dev/null && echo "已存在 → 投递" || echo "新建 → 可写"
   ```
   具体：支线可**新建** `shared/` 下的脚本 / 凭据 / 工具文档；**已存在的一切文件（含支线自己刚建的那个脚本）一律投递**——**没有例外**（`CURRENT.md` 多写者例外曾开过一届即废，教训见 [lessons.md](lessons.md) §五.17–18）。
   - **为什么"修改"必须投递**：同一工作树里两个会话改同一文件是 **last-write-wins**（不是 merge 冲突），覆盖**无任何警告**。
2. **支线不碰三个共享索引**：根 `README` 的「最近动态」/ 项目 `state.md` / `history.md` 索引——只有主线程在轮次边界改。
3. **轮次号只由主线程分配**：支线不占号，其投递物在整合时才被编入某一轮。
4. **支线投递后自己提交一次**：commit message 标「支线投递：<主题>」，**只含本支线自己的文件（`inbox/` 里的投递物 + 依 §一.1 新建的文件）**。理由：① 避免被主线程收尾的 `git add -u` 提交扫入；② **让内容进入 git，成为"被覆盖后还能取回"的前提**（§三.10 恢复程序对未提交即被覆盖的内容无能为力）——本条**不是可选步骤**。**与"轮次收尾才提交"不冲突**：收尾第 8 步的 `exit 0` 门槛只约束「轮次收尾提交」，支线投递提交必然让第 11 项（inbox 待整合）报红，那是它的职责。
5. **同一张表的改动不硬合**（**同一文件同理**）：支线若要改主线程正在改的同一张表 / 同一文件，写进投递物由主线程整合——**改表的语义判断需要主线程手上的证据链**。
6. **支线的临时产物同样进 `inbox/scratch/`**（不得落 `/tmp`，见 §执行与清理纪律第 1 条）——**投递物与临时产物是两回事**：投递物是待整合的内容（放 `inbox/` 根），临时产物是中间文件（放 `inbox/scratch/`）。

### 二、同步机制（靠两条独立通道，不能只靠一条）

7. **通道 A —— `projects/<项目>/history/CURRENT.md`（软通道，事先声明，单写者）**：**只由主线程写**——每轮开始时写本轮主题与「在改」文件清单，**收尾时清空**（含页脚"最近一次填写"）。**支线不写它**。**投递物的登记表就是 `inbox/` 本身**，不另设副本。
8. **通道 B —— `git log --oneline -5` + `git status --short`（硬通道，不依赖对方）**：**任何会话在写文件之前都要跑这两条**。`CURRENT.md` 可能没被写、可能过期——**硬通道是底线**。
   - **判据**：若目标文件在**最近几条提交**里被动过、或工作区里有**未提交的改动落在你要改的文件上** → **停手**：投递给对方，或先问用户。**不要覆盖**。
9. **投递物必须按 [templates.md](templates.md) §支线投递物 的结构写**（含"已提交的产出 / 待安装的规则 / 待处理的遗留 / 证据等级"四节）——**没有结构就没有可整合的接口**。

### 三、冲突已经发生时怎么办

10. **恢复程序**：`git log --oneline` 找到覆盖前的那次提交 → `git checkout <commit> -- <被覆盖的文件>`（若覆盖内容**尚未提交**，用 `git checkout HEAD -- <file>`）→ **恢复后立即 `diff` 或比对体积确认取回的是原文件**，并把事故与恢复写进该轮轮次记录（[rounds-57.md](../projects/autonomous-driving/history/rounds-57.md) §事故是范例）。
11. **恢复优先于续写**：发现覆盖后**先恢复再继续**，不要在损坏的版本上接着改——否则会把错误固化进下一次提交。

### 四、投递物的归宿

12. **主线程整合后移入 `archive/`**，命名 `archive/YYYY-MM-DD-支线交付-<主题>.md`，并在**文件头加一段归档说明**（整合到哪些文件、由哪一轮整合、下文相对链接按当时位置可能失效）——**归档件是历史记录，保持原样、不回改**。

> **与孤儿检查的关系**：支线投递物在被整合前**没有入链是正常的**，故 `check_links.py` 的**孤儿检查豁免 `inbox/`**（与弱引用检查豁免 `raw/` 同理）。

## 文件更新

- 有实质性新资料、约束变化、核验结果或研究决定时更新对应文档
- 有实质性进展、决策或新增等待事项时，同步更新根目录 `README.md` 的「最近动态」与「等待用户」
- **README 的「最近动态」每条只留 1–2 行指针**（"做了什么 + 结论指向哪个文件"），不写结论本身；条目累积到读不完时压缩为一行式指针表，细节溢出到项目 `state.md` / `history.md`
- **文件尺寸预算**（判定阈值有三条，**任一超限都算超限**）：
  1. `index.md` / `state.md` ≤ **100 行**
  2. **任何文档 ≤ 64 KiB**（65536 字节）——**Read 工具一次可整读的物理上限，硬约束、不可上调**；由 `check_links.py` 第 12 项机器检查。**两线制**：
     - **硬线 64 KiB**：超 = 违规、参与 exit code，**收尾前必须处理**（确实修不完的，按 [workflows.md](workflows.md) §轮次收尾第 7 步在提交信息里记"已知告警"）。
     - **预警线 60 KiB**：进入 = 预警（**只报不阻断**），留约一轮增量余量。
     - **零和编辑纪律（第七十八轮加）**：预警带内的文件，编辑必须**零和或负和**（新增 N 字节须同步删 ≥N 字节）；需要正和追加时，先瘦身腾出空间再追加，或把内容改道到其他文件（先例：`sota-plan` 的结论改落 `recombination-map`）。
     - **超限处理按文件角色分档**（**不一律拆册**）：
       ① **索引/登记类**（`history.md`、`index.md`、`sources.md`、各 README）→ **瘦身**（价值在"可扫"，详情已在别处，压缩为指针），**不拆册**；
       ② **脉络/清单类**（`lineage.md`、`transfer.md`、`code/traces/*`、`papers.md`）→ **拆册**（`X-2.md`，见 [templates.md](templates.md) §分册、编号与更正约定）；
       ③ **决策/交叉引用稠密类**（`sota-plan.md`、`preparation.md`、`judgments.md`）→ **优先瘦身去重**；瘦身后仍超线、且找得到"引用最少"的章节边界时才拆册（错册代价的实例见 [lessons.md](lessons.md) §三.9）。
  3. 论文笔记一篇一文件
- `state.md` 超限有两种形态：**行数超限**（拆出 `history.md`）与**行数合规但体积超限**（拆出 `judgments.md`，`state.md` 只留分组索引）
- 不记录每一句聊天
- 重要结论被修正时保留修正原因和原依据
- 已放弃的 idea 与失败实验保留记录后移入 archive
- **单一事实源**：同一信息只允许一处权威副本。**证据等级以本文档为准**、工作空间组织以 [`shared/workspace-design.md`](../shared/workspace-design.md) 为准、清理纪律以本文档 §执行与清理纪律为准；其他文件只写指针，不重复正文。

## 主动优化

- 发现工作空间结构问题（重复副本、死链、超限文件、状态失真）或效率/产出改进机会时，主动向用户提出优化请求，不等询问
- 用户已确认：此类提议的讨论与执行成本可接受，判断标准只有效率提升与产出提升
- **健康自检**（结构变动后或用户要求时）：审计死链、孤儿文件、`state.md` 失真、超限文件（含 64 KB 阈值）、单一事实源违反。批量改写前先确认**工作空间版本库是干净的**（`git status --short` 为空，或改动已提交）——这样任何改写都能 `git diff` 复查、`git checkout` 回滚。

## 跨对话恢复

每次开始工作按 AGENTS.md 指定的入口读取，当前用户指令优先于历史记录。

## 执行与清理纪律

### 只读操作的工具选择

读取文件使用内置 Read，搜索文本使用 Grep，定位文件使用 Glob，批量读取使用 Read 批处理。**禁止用命令行读取文本、搜索内容、列举文件或统计行数/体积**。命令行仅用于内置工具无法完成的程序执行、检查或产物生成；使用前说明具体缺口并把命令范围收窄。内置工具因权限边界不可用时，不得绕道命令行，应暂停该项读取并说明阻塞。

（本节的由来与"临时根为何从 `/tmp` 迁回工作空间"的完整教训见 [lessons.md](lessons.md) §二。）

1. **单一临时根**：所有中间产物（PDF、解压文本、下载的 tarball、检索脚本、子代理缓存）一律放 **`inbox/scratch/`**（工作空间内，已被 `.gitignore` 忽略、已被 `check_links.py` 的 `SKIP_DIRS` 跳过），不再新建其他临时目录；一次性目录（如 `tar_test`）用完不建，直接用同一根。
2. **流程中不做删除**：重试脚本不写 `rm -rf`。失败时改为换名重试（`<name>.try2`）或跳过并记录；删除动作只允许出现在收尾阶段。
3. **收尾一次性清理**：需要删除的内容累积到 `inbox/cleanup.md`；收尾（或一天一次）时把清单写成**一条命令**，用户只授权一次。
4. **工作空间内删除要批量**：需要删工作空间文件时，用一次 `DeleteFile` 提交多个路径，不逐个删。
5. **命令尽量合并**：把多步操作写成一条 shell（`&&`、循环、脚本文件），减少调用次数即减少授权次数。**一次性脚本写进 [`shared/scripts/`](../shared/scripts/) 再执行**（可复现、可复查），不用 heredoc。
6. **只读优先**：能用 Read/Grep/Glob 完成的不起 shell；能在沙箱内跑的不加 `dangerouslyDisableSandbox`；**需要指定目录时用工具的 `cwd` 参数，不要在命令里写 `cd`**。每次 Shell 调用都要能说出"为什么不能用专用工具"。
7. **不留垃圾**：失败的重试目录、临时解压目录要在收尾清单里显式列出。**scratch 清理口径**：`inbox/scratch/` 内**已完成使命的一次性产物**（结论已落盘并提交）在收尾时**批量清除即可**（`rm -rf` 仅限 scratch，见第 10 条），**不必登记 `cleanup.md`**——该表只管两类：git 跟踪文件（走 `git rm`）与**工作空间外**路径。
8. **不可逆操作前先备份**：批量改写、文件拆分、批量替换等**无法回滚**的操作，**先 `cp` 一份到 `inbox/scratch/`**，完成后立即做两项验证——① **体积守恒**（拆分后各册体积之和 ≈ 原文件体积，不等即回滚）；② **死链检查**。（原始事故与"轮次记录 + judgments 是可重建安全网"的由来见 [lessons.md](lessons.md) §一.2。）
9. **每轮收尾提交一次 git**：工作空间已 `git init`，**`.gitignore` 忽略 `projects/*/code/repos/`（1.6 GB 第三方快照）、`inbox/scratch/`、`.trae/`**（另有凭据 `shared/tools.env` 与 IDE/`__pycache__` 类忽略，完整清单见 `.gitignore`）。
   - **提交时机**：**每轮收尾**（[`ai/workflows.md`](workflows.md) §轮次收尾第 8 步），与 [check_links.py](../shared/scripts/check_links.py) 同批做（**检查项清单见脚本 docstring，本文件不枚举、不写数字**）。
   - **提交信息**：首行 = `第 N 轮：<一句话>`；正文写**改了什么、为什么**，并注明本轮产出的文件。**前缀规范三类**（可机器区分主线与支线）：`第 N 轮：` / `支线投递：` / `工具：`。
   - **提交命令**（**用 `-c` 传身份，不写任何 git config**）：
     ```
     git add -u && git add <本轮新增的文件路径> && git -c user.name=verse -c user.email=verse@localhost commit -m "第 N 轮：..."
     ```
     **不用 `git add -A`**：`-A` 会**静默扫走支线未提交的半成品**（同工作树是 last-write-wins，无警告）。改为 `-u`（已跟踪文件的改动）+ **显式列新文件**。**不写 `cd`**——Shell 工具的 `cwd` 默认就是工作空间。身份 `verse <verse@localhost>` 是默认值（本机无 git 身份配置）。
   - **推送远端**（2026-10-04 起远端已建）：提交后 `git -c http.proxy=http://127.0.0.1:7897 push origin master`——`github.com` 直连不通，须带代理（用 `-c http.proxy`、不依赖全局 `https_proxy`）；凭据从 `shared/tools.env` 的 `GITHUB_TOKEN` 读，**不写进 `.git/config`**。详见 [tools.md](../shared/tools.md) §网络访问。
   - **轮次打 annotated tag**：`git tag -a round-N -m "<一句话>"`——让正文里"见第 N 轮"能落到 `git show round-N`。
   - **与第 8 条的关系**：有了 git，任何批量改写都能 `git diff` 复查、`git checkout` 回滚；第 8 条的 `cp` 备份防的是"未提交的工作丢失"。**两者并存**。
10. **危险命令自守**（权限放宽后**"命令审批"就是最后一道闸**，自守承诺写成纪律、不靠临时判断）：
   - **破坏性 git**（`reset --hard` / `clean -f` / `push --force` / `branch -D` / `checkout --`）：**即使沙箱允许，也先问再做**。
   - **`rm -rf`**：**只对 `inbox/scratch/` 用**；其余一切删除走 `inbox/cleanup.md` 累积 + 收尾一次性授权（即第 2、3 条）。
   - **`sudo` / 系统包安装 / `systemd` / `docker` / 改 `~/.bashrc`**：**只给命令，由用户自己执行**（`~/.bashrc` 沙箱本身也拒绝写）。
   - **覆盖无闸**（写文件不弹审批）⇒ 搞丢成果的真实路径是**覆盖**不是删除——版本控制（第 9 条）+ 异地副本是唯一解（实测记录见 [lessons.md](lessons.md) §一.3）。
