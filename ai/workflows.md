# AI 工作流

证据等级的定义见 [rules.md](rules.md) §证据等级（**不在此重复**）。

## 文献检索

1. 确认检索范围和关键词；**记录查询式与去重后篇数**（供复核，写进 `raw/` 检索日志）
2. 多源检索（arXiv, OpenAlex, Crossref, 出版社页面）
3. 去重、记录版本关系（同名不同篇、会议版与预印本版要分清）
4. **按质量分档筛选**（T1–T5，口径见 [shared/literature-quality.md](../shared/literature-quality.md)）——**未发表的预印本**用"强团队 +（有代码 或 方法独特）"口径；**已发表**优先看 CCF 评级与引用量
5. 按主题分级（A=直接相关，B=广义相关，C=专题补充，D=待核验）
6. **venue 三渠道并行核验**（见 [rules.md](rules.md) §venue 核验）——`comments` + OpenAlex 按标题 + Crossref 按 DOI；**"Submitted to" ≠ 录用**
7. 输出结构化表格并登记到来源索引
8. **边界外清单要定期复核**：列在"边界外"的条目不是永久排除，团队/venue/代码状态变化时逐条重判（实测 15 条复核里有 9 条应升为正式收录）

## 论文精读（摘要 → 全文）

1. 摘要级只记"作者自己声称什么"，**不记数字**
2. 升全文后：**先核表格数字**（PDF + `pdftotext -layout` 逐格），再读方法节
3. **必须区分受控消融与榜上对比**——同一张表里两行不同方法的差值**不能归因到机制**（实测一处误读：把 Table 1 两行不同方法的 24.2→55.5 当成"换条件带来的收益"，真实受控收益只有 +3.7）
4. 每条关键事实标注 `表号/节号`，便于回查
5. **每篇的结论落到"对本项目意味着什么"**，否则只是读书笔记

## 代码脉络梳理

1. 固定论文版本和代码 commit
2. 识别基线模型（继承关系）
3. 识别引入的模块来源（组合关系）
4. 核验论文核心创新点对应的代码改动（对应关系）
5. 记录可比较条件：输入、输出、监督、评价协议
6. **标注代码核验级别**（L1 逐文件 / L2 仓库存在性 / L3 API+raw 未克隆，见 [rules.md](rules.md) §代码静态检查）
7. **专门找"名字 ≠ 实际"**——已积累七类陷阱：① 配置覆盖链 ② 声明未接线 ③ 零权重 ④ 死引用 ⑤ 被注释关闭 ⑥ 命名与实现语义不符 ⑦ **论文机制落在"评测路径没 import 的版本"里**（实测 GuideFlow：CVF 只在 v8、RFE 只在 v10，而评测 import 的是 v6）
8. **负面结论同等重要**：零代码、机制未发布、权重为 0、数字不可复现，都要写进表与脉络，**不能只记正面发现**

## 脉络梳理（lineage）

产出物：领域层 `direction/lineage.md`、小方向层 `topics/<x>/lineage.md`。模板见 [templates.md](templates.md)。

1. **先表后脉络**：先把论文表（事实）建完，再写脉络（判断）；脉络里只写判断，事实留在表与笔记，不重复
2. **阶段划分要给出分界标志**，不能只按年份切；分期方式本身可能有分歧（不同综述用不同切法），要写明分歧而不是抹平
3. **每条"关键转移"回答三问**：之前是什么、之后是什么、我的判断是什么
4. **未解决问题标注"谁明确提出"与证据等级**，不写成自己的判断
5. **章节末必须有「证据边界」**：哪些是论文自述、哪些经代码核验或实际运行
6. **只给领域整体与研究对象写厚脉络**；借鉴来源写薄脉络（阶段 + 关键节点 + 与研究对象接口的差异）

## Idea 讨论准备（2026-09-23 定）

讨论前的准备材料集中在一份 `ideas/preparation.md`，结构固定为：

1. **研究地图**：这个子方向在做什么（主线 + 横切轴）
2. **可作为设计前提的已验证事实**：每条标证据等级；**与 `judgments.md` 不重复**——此处只留"对设计有约束力"的条目并指向 `judgments.md`
3. **明确未解决的问题**：附"谁明确提出"（P1、P2…编号可被方向引用）
4. **可迁移机制**：独立成 `transfer.md`，本文只放入口指针
5. **潜在方向空间**：每条给出「依据 → 重合风险 → 最小验证实验 → 需要什么 → 停止条件」五要素
6. **比较口径**：讨论前必须先固定的规则（基准划分、输入权限、输出模态、命令维）
7. **需要用户决定或补充的信息**

**纪律**：
- **每条方向必须写"重合风险"**，且要基于代码级核验而非摘要——已多次出现"初判空白、核验后空间变小"（如"约束注入层级选择"）
- **收益量级要横向对齐**：把各机制轴的受控收益放在一起比（实测四条轴都在 +3.7 ~ +6.7，**没有一轴远大于其他轴**），避免把某个方向当成显然更优
- **不自动升级候选 idea 为选定方向**（见下）

## Idea 验证

1. 检查候选 idea 与已有工作的重合
2. 检查数据是否提供所需监督信号
3. 检查环境是否允许验证
4. 估计实验成本和失败回退成本
5. 明确停止条件
6. 不自动升级候选 idea 为选定方向

## 实验

1. 固定环境版本、数据版本、评价协议
2. 记录训练配置、超参、随机种子
3. 区分受控比较与系统级比较
4. 实验失败不等于 idea 错误；记录失败原因和调整建议

## 轮次开始（pre-flight，2026-09-30 第六十二轮新增）

开工前花几秒做三件事——**收尾检查管"本轮产出对不对"，开轮检查管"本轮是不是基于旧信息"**：

1. **`git status --short` 应为空**——非空说明**有别的会话未提交的活**，先问清再动（同一工作树是 last-write-wins，**覆盖无警告**）。
2. **`ls inbox/*.md`（去掉 `cleanup.md`）**——有投递物就**只看主题**判断是否与本轮要改的相关；**相关者先整合，不相关则本轮不动**。
3. **读 [CURRENT.md](../projects/autonomous-driving/history/CURRENT.md) 的「在改」区**——若别的会话正在改你也要改的文件 → 改期，或只投递（见 [rules.md](rules.md) §支线协作纪律）。

**为什么只在开轮查一次、不随时查**：一轮要写几十个文件，逐个查是纯噪音；而"每次都要记得"这类约定，**正是本工作空间反复证明会失效的那一类**（第 49–54 轮漏了收尾步骤且无警报）→ 所以它由**第 11 项机器检查兜底**（收尾时非 0 即报）；开轮这一步只负责"**早点发现、避免返工**"。

## 轮次收尾（每轮必做，2026-09-23 定）

一轮工作结束前，**同一批事实要同步到所有"手写当前态"的位置**，否则下一轮会读到互相矛盾的数字（实测一次抽查就查出 7 处 stale，其中 1 处与事实直接矛盾）：

1. `history/rounds-NN.md`：本轮做了什么、更正了什么（**细节只写这里**）
2. `state.md`：阶段、待续清单、判断边界索引（行数与体积都要在预算内）
3. `index.md` 与 `README.md` 的"最近动态"：只留 1–2 行指针，不写结论
4. **各 `topics/<x>/README.md` 的「状态」字段与「产出状态」节**——最易漏。实测一次抽查发现 VLA 侧停在"两轮 / 18 篇"、世界模型侧停在"三轮 / 9 篇全文"，而实际已是四轮 / 28 篇 / 24 篇
5. **`project.md`**：只写定义与边界；**进度一律写成指针**（"以 `state.md` 为准"），不复述易失真的数字
6. **计数类事实先找权威源**：仓库数 → `code/repositories.md`；来源与代码可用性 → `sources.md`；论文与笔记篇数 → 各 `papers.md`。其余文件引用时必须指向它，**历史数字要加"当时 N 个"的限定**，否则会与当前值混淆
   - **同一份"清单"只允许一个权威版本，其余一律只留指针**（2026-09-24 第三十三轮补）：实测 `judgments.md` 的 **"RL 词义核验"清单**在**三条**里分别写成 **3 / 5 / 9 种**、且全是现在时（第三十三轮统一为九种 + 指针）；另一处"非生成式基线"在**同一条目内**标题写"三种"、正文写"扩到五种"。→ **凡"扩到 N 种 / 第 N 例"这类随轮次增长的计数，旧位置必须改成指针或加"当时 N 种"限定**；这与"引用类"（同一篇论文在多处出现）不同——**引用可以重复，计数不能**
7. 复跑检查：**跑 [shared/scripts/check_links.py](../shared/scripts/check_links.py)**——**逐项清单、以及每项的动因（为什么加它、当初踩了什么坑）一律见脚本 docstring 与内联注释，本文件不重复、不写数字**（第六十五轮收敛：此前这份清单在 `脚本 / shared/index.md / 本文件` **三处各写一遍**，"十项 / 十一项 / 十二项"这个**数字也三处各写一次** → 加一项要改三处，**已实际漏过两次**，见第 62、64 轮）。**判据只有一条：`exit 0` 才算通过**；任一项不过即 `exit 1`，明细打印在输出里。
   - **⚠ 本步必须在第 9 步（整合 inbox）之后跑**（第六十七轮理正）：第 11 项度量的是"**待办状态**"（`inbox/` 有待整合即报），**不是"缺陷"**——若先跑本步再整合，第 11 项必然还报红、`exit 1`，与第 8 步"必须在 `exit 0` 之后提交"直接卡死（此坑已实际发生多次而未被察觉）。**两条出路**：① 把整合放前面（推荐：`ls inbox/` → 整合 → 跑本步 → 提交）；② 已先跑过本步的，整合后**重跑一次**再提交。
   - **不过怎么办**：先修再提交（第 8 步）；确实修不完的，在提交信息里写明"已知告警：…"。
   - **两条写作约定**（它们不是"检查的实现"，而是"写文档时要守的规矩"，故留在流程里）：① **一篇论文有笔记，就要在它出现的论文表行、脉络或 `repositories.md` 里留一个指针**——否则读论文表的人根本看不到这些论文有全文笔记；② **拆册后先跑这项**——`§X` 挂错文件**死链检查抓不到**（文件确实存在），**换 basename 拆册尤其要跑**（这类坑已踩三次，累计 52 / 13 / 17 处）。
   - **登记表随内容更新**：脚本里有两张**显式登记表**——「声明计数 vs 权威源」的 `COUNT_RULES` 与「CSV↔md」的 `CSV_ID_PAIRS`。文档措辞改了要同步改登记表；**"声明处没匹配到"也会报出来**，那正是"该更新登记表"的信号。
   - **同一事实的一致性顺手抽查**：跨文件对同一数字/结论的说法（第二十八轮这样查出 8 处冲突，含"去掉世界模型"却用"加上"的箭头方向）——**新写的事实若推翻了旧结论，必须就地标 `⚠ 更正` 并保留原依据**。
8. **提交 git（第四十八轮新增；第六十二轮改 `add` 方式；第六十五轮把命令收敛）**：**命令本身、身份怎么传、为什么不用 `git add -A`、提交前缀三类、轮次 tag、`.gitignore` 三条忽略——完整要求见 [rules.md](rules.md) §执行与清理纪律第 9 条（那是「执行与清理纪律」的唯一定义处），本文件不复述**。
   - 本步只记**两条顺序**要求：① **必须在第 7 步 `exit 0` 之后**（检查全绿才提交，否则把坏状态固化进历史）——**此门槛只约束「轮次收尾提交」，不约束支线投递提交**（见下）；② **必须在第 9 步整合完 inbox 之后**（否则整合出的改动进不了本次提交）。两条合起来把顺序钉成 **→ 9（整合）→ 7（检查，在整合之后）→ 8（提交）**，或等价的"整合 → 复跑检查 → 提交"。
   - **⚠ 支线投递提交不受 `exit 0` 门槛约束**（第六十七轮补）：支线的职责就是往 `inbox/` 放投递物 → 第 11 项**必然**报红，**这是它的职责、不是缺陷**（[rules.md](rules.md) §一.4 要求它投递后立即提交，为的是让内容进 git 以备恢复）。**支线提交前不必、也无法把第 11 项变绿**——不要因此误判成"规则矛盾"。
   - **提交前自查**（操作动作，只在流程里）：`git status --short` 里**不该出现** `code/repos/` 或 `inbox/scratch/` 下的任何文件——出现即说明 `.gitignore` 漏了。
   - 提交信息写"**改了什么、为什么**"，不要只列文件清单——半年后需要的是"当时为什么这么改"（与 [workspace-design.md](../shared/workspace-design.md) 运行纪律第 7 条「决策留痕」一致）。
9. **整合 inbox 投递物（2026-09-30 新增，第六十一轮补强，见 [rules.md](rules.md) §支线协作纪律）**：**直接 `ls inbox/`**（第六十七轮起：**投递物的登记表就是 `inbox/` 本身**，`CURRENT.md` 不再登记投递物、恢复单写者，见 [rules.md](rules.md) §二.7）→ 把投递物里的**事实**整合进对应表 / 脉络 / `state.md`，并在本轮 `rounds-NN.md` 里写明"**整合了哪些投递物**"。
   - **顺序**：本步**应在第 8 步提交之前、并在第 7 步复跑检查之前完成**（否则整合出的改动进不了本次提交，且第 11 项不会归零）；整合产生的改动与该轮改动**同一次提交**。
   - **投递物 ≠ 临时产物**：投递物在 `inbox/` 根（待整合、有意义），临时产物在 `inbox/scratch/`（中间文件、直接被忽略）——**别把投递物当 scratch 删掉**。
   - **投递物里的"事实"要复核再落盘**，不能照抄：支线可能只有单侧证据（本次实测一处——投递物称"已写进 `tools.md`"，实际 `tools.md` 里没有，且旧文字与新证据相反）。
   - **归档（第六十二轮扩为三种处置）**：**`inbox/` 只放"待处理"，不放"已处理"**——否则**第 11 项检查每轮报同一篇，几轮后就被无视**（所有"永久报警"的检查都是这个宿命）。

     | 处置 | 动作 |
     |---|---|
     | **采纳** | 整合进表 / 脉络 / `state.md` → 移入 `archive/YYYY-MM-DD-支线交付-<主题>.md` |
     | **否决** | 移入 `archive/` + **在本轮 `rounds-NN.md` 写明否决理由** |
     | **搁置** | 移入 `archive/` + 注明"**搁置，见第 N 轮**" |
   - **归档件要加文件头说明**（整合到哪些文件、由哪一轮整合、下文相对链接按当时位置可能失效），**原样保留、不回改**。
   - **收尾 `CURRENT.md`**（第六十七轮改）：该文件现只有「在改」区（主线程单写者）——整合完把本轮「在改」区清空即可；**不再有「待整合投递」区**（已废，见 [rules.md](rules.md) §二.7）。

## 写作

1. 区分"论文声称"与"已验证结果"
2. 代码未核验或实验未完成时标注为"初步"或"待验证"
3. 不把检索未发现重合当作已证明新颖
