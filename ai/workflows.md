# AI 工作流

证据等级的定义见 [rules.md](rules.md) §证据等级（**不在此重复**）。

## 文献检索

1. 确认检索范围和关键词；**记录查询式与去重后篇数**（供复核，写进 `raw/` 检索日志）
2. 多源检索（arXiv, OpenAlex, Crossref, 出版社页面）
3. 去重、记录版本关系（同名不同篇、会议版与预印本版要分清）
4. **按质量分档筛选**（T1–T5，口径见 [shared/literature-quality.md](../shared/literature-quality.md)）——**未发表的预印本**用"强团队 +（有代码 或 方法独特）"口径；**已发表**优先看 CCF 评级与引用量
5. 按主题分级（A=直接相关，B=广义相关，C=专题补充，D=待核验）
6. **venue 三渠道并行核验**（见 [rules.md](rules.md) §venue 核验）——`comments` + OpenAlex 按标题 + Crossref 按 DOI；**"Submitted to" ≠ 录用**
7. 输出结构化表格并登记到来源索引
8. **边界外清单要定期复核**：列在"边界外"的条目不是永久排除，团队/venue/代码状态变化时逐条重判（实测 15 条复核里有 9 条应升为正式收录）

## 论文精读（摘要 → 全文）

1. 摘要级只记"作者自己声称什么"，**不记数字**
2. 升全文后：**先核表格数字**（PDF + `pdftotext -layout` 逐格），再读方法节
3. **必须区分受控消融与榜上对比**——同一张表里两行不同方法的差值**不能归因到机制**（实测一处误读：把 Table 1 两行不同方法的 24.2→55.5 当成"换条件带来的收益"，真实受控收益只有 +3.7）
4. 每条关键事实标注 `表号/节号`，便于回查
5. **每篇的结论落到"对本项目意味着什么"**，否则只是读书笔记

## 代码脉络梳理

1. 固定论文版本和代码 commit
2. 识别基线模型（继承关系）
3. 识别引入的模块来源（组合关系）
4. 核验论文核心创新点对应的代码改动（对应关系）
5. 记录可比较条件：输入、输出、监督、评价协议
6. **标注代码核验级别**（L1 逐文件 / L2 仓库存在性 / L3 API+raw 未克隆，见 [rules.md](rules.md) §代码静态检查）
7. **专门找"名字 ≠ 实际"**——已积累七类陷阱：① 配置覆盖链 ② 声明未接线 ③ 零权重 ④ 死引用 ⑤ 被注释关闭 ⑥ 命名与实现语义不符 ⑦ **论文机制落在"评测路径没 import 的版本"里**（实测 GuideFlow：CVF 只在 v8、RFE 只在 v10，而评测 import 的是 v6）
8. **负面结论同等重要**：零代码、机制未发布、权重为 0、数字不可复现，都要写进表与脉络，**不能只记正面发现**

**继承关系的强度分级（2026-10-01 第七十三轮定）**：脉络里的「继承关系」按证据强度分四级——**S1 硬继承**（类继承 `class X(Y)`、fork、逐行对照坐实的代码派生）、**S2 自述派生**（README / 论文写 `based on` / `built upon` / `following`）、**S3 模块复用**（抄损失函数、vendored 代码、同名锚点/词表）、**S4 团队延续**（仅同团队/同机构，**必须标"推断"**）。每条继承关系都要标强度，缺证据的降为 S4。

## 脉络梳理（lineage）

产出物：领域层 `direction/lineage.md`、小方向层 `topics/<x>/lineage.md`。模板见 [templates.md](templates.md)。

1. **先表后脉络**：先把论文表（事实）建完，再写脉络（判断）；脉络里只写判断，事实留在表与笔记，不重复
2. **阶段划分要给出分界标志**，不能只按年份切；分期方式本身可能有分歧（不同综述用不同切法），要写明分歧而不是抹平
3. **每条"关键转移"回答三问**：之前是什么、之后是什么、我的判断是什么
4. **未解决问题标注"谁明确提出"与证据等级**，不写成自己的判断
5. **章节末必须有「证据边界」**：哪些是论文自述、哪些经代码核验或实际运行
6. **只给领域整体与研究对象写厚脉络**；借鉴来源写薄脉络（阶段 + 关键节点 + 与研究对象接口的差异）

## Idea 讨论准备（2026-09-23 定）

讨论前的准备材料集中在一份 `ideas/preparation.md`，结构固定为：

1. **研究地图**：这个子方向在做什么（主线 + 横切轴）
2. **可作为设计前提的已验证事实**：每条标证据等级；**与 `judgments.md` 不重复**——此处只留"对设计有约束力"的条目并指向 `judgments.md`
3. **明确未解决的问题**：附"谁明确提出"（P1、P2…编号可被方向引用）
4. **可迁移机制**：独立成 `transfer.md`，本文只放入口指针
5. **潜在方向空间**：每条给出「依据 → 重合风险 → 最小验证实验 → 需要什么 → 停止条件」五要素
6. **比较口径**：讨论前必须先固定的规则（基准划分、输入权限、输出模态、命令维）
7. **需要用户决定或补充的信息**

**纪律**：
- **每条方向必须写"重合风险"**，且要基于代码级核验而非摘要——已多次出现"初判空白、核验后空间变小"（如"约束注入层级选择"）
- **收益量级要横向对齐**：把各机制轴的受控收益放在一起比（实测四条轴都在 +3.7 ~ +6.7，**没有一轴远大于其他轴**），避免把某个方向当成显然更优
- **不自动升级候选 idea 为选定方向**（见下）

## Idea 验证

1. 检查候选 idea 与已有工作的重合
2. 检查数据是否提供所需监督信号
3. 检查环境是否允许验证
4. 估计实验成本和失败回退成本
5. 明确停止条件
6. 不自动升级候选 idea 为选定方向

## 实验

1. 固定环境版本、数据版本、评价协议
2. 记录训练配置、超参、随机种子
3. 区分受控比较与系统级比较
4. 实验失败不等于 idea 错误；记录失败原因和调整建议
5. **失败实验同等登记（第七十八轮加，论文 claims 的弹药）**：失败实验与成功实验**同规格落盘** `experiments/records/<run_id>.md`，四要素 = **假设 / 观测现象 / 已排除原因 / 对 idea 的影响**——失败是排除路径的证据（rebuttal 与消融叙事直接引用）；与第 4 条衔接：先按四要素归因，再判"idea 错误"还是"实现/环境问题"。
6. **复现声明（第七十八轮加，投稿前自查的最后一块地基）**：论文正文每个数字须可溯源到四要素 = **随机种子 / 硬件 / checkpoint 来源与哈希 / 评测代码 commit**——与 [sota-plan.md §10](../projects/autonomous-driving/ideas/sota-plan.md)（对比协议与六项口径）及 [experiments/protocol.md](../projects/autonomous-driving/experiments/protocol.md)（预注册协议）互指；协议里已固定的口径（如 `EPDMS` 实现版本）**不得在论文里 silently 换口径**。

## 周扫（每周一次的外部复核，2026-09-30 第七十轮定）

**定位**：周扫**不是**"增量读论文"，而是**对工作空间里「易失效的断言」做定期外部复核**，外加增量扫描新工作。**易失效断言有三类**：① **"无代码 / 未发布"标签**；② **榜单数字与格局**；③ **venue 与代码可用性**。
**依据（首次实测）**：2026-09-30 两张几天前刚建的表里，**"无代码"标签当天就有 3 条被推翻**；`sota-plan.md` §1 的 13 行分数格局与官方实时榜差到 **"榜首完全换人、且榜一根本不在榜上"**（见 [§1.0](../projects/autonomous-driving/ideas/sota-plan.md)）。

**触发**：用户说一句「跑周扫」→ 主线程起 **1–3 个只读子代理**（用最便宜的模型）。**不自动定时**——节奏由用户控制。

**三条线**（按实测命中率排序）：

1. **榜单线**（**每次周扫必跑**，成本 = 1 次 POST；触发节奏由用户控制，见上「触发」节）
   ```bash
   export https_proxy=http://127.0.0.1:7897 http_proxy=http://127.0.0.1:7897
   curl -X POST -H "Content-Type: application/json" -d '{"lb":"public"}' \
     https://agc2025-e2e-driving-navhard.hf.space/leaderboard
   ```
   返回 `{"response": "<markdown 表>"}`，字段：`rank` / `id`（**代码链接以 `<a href=...>` 内嵌在 id 里**）/ `extended_pdm_score_combined` / 18 个子指标（stage_one/two 各 9）/ `submission_datetime`。
   动作：与 [sota-plan.md §1.0](../projects/autonomous-driving/ideas/sota-plan.md) 的快照 diff → 报**新增条目 / 分数变化 / 新放代码**。健康检查 `GET /competition_info`；降级方案（接口被关时）= SimScale README 的 navhard 表作代理信号。
   - **⚠ 两处易错**：gated 的是**数据集**（`AGC2025/e2e-driving-navhard`，匿名 401），**不是 Space 本体**（`gated:false`）；`{"lb":"private"}` 需比赛结束 + OAuth，**不可读**。
   - **⚠ 快照必须带取数日期**——榜单每天都在变（2026-09-30 取的 20 行里有 11 行是当月提交）。
2. **代码线**（**实测命中率最高**）
   - 名单**自动从工作空间派生**：所有记「无代码 / 未发布 / 占位仓库 / 只有项目页 / 代码不全」的条目（来源：`sota-plan.md`、`code/repositories.md`、各 `papers.md`）。
   - **检索必须双通道**：`GET /search/repositories?q=<方法名>` **＋** `GET /repos/<org>/<方法名>`。**翻案的根因就是只按论文 `comments` 里的链接判定、没做方法名检索**（实测：`valeoai/DrivoR` 早在 2026-01 就存在，而本空间写的是"无仓库、无 project page"）。
   - **⚠⚠ 反方向的错也要防——"仓库存在" ≠ "有代码"**：实测 `Rtwotwo/DriveTTO` 是 **5 KB 占位仓**（只有 LICENSE + README "Paper and code coming soon"），却被当成"有代码" → **必须看 `contents` 里有没有实际源码，不只看仓库 200**。
   - **看榜上链接也要小心**：链接指向**项目页** ≠ 无代码（TOAD / DrivoR 都是只链项目页、实有仓库）。
   - 已确认项记入**排除表**，避免每周重复报。
3. **论文线**
   - arXiv API：`curl -L`（**`http://` 会 301，必须跟跳转**；`python urllib` 会被 406）。
   - **首跑回溯 30 天，之后固定 7 天**（实测 7 天只覆盖 30 天入报量的 28%，且 15–30 天区间边际收益未饱和）。
   - **不限分类**：加 `cat:cs.RO OR cat:cs.CV` 只砍噪声、却会漏 `cs.AI`-only 的驾驶论文（实测一例）。建议放宽为 `cs.RO OR cs.CV OR cs.AI OR cs.LG`，靠标题二次过滤。
   - 查询词：`end-to-end driving` / `diffusion planner` / `trajectory scoring` / `trajectory vocabulary` / `VLA driving` / `world model planning` / `NAVSIM` / `navhard`。
   - 去重后**只留三类**：① 与候选方向撞车 ② 动摇已落盘结论（数字/榜单）③ 高质量且与研究对象直接同构。

**成本上限**：子代理 ≤ 3 个；GitHub API ≤ 60 次（搜索端点 30/分钟）；arXiv ≤ 12 次查询；**产出条目 ≤ 8 条**；缓存落 `inbox/scratch/`。

**产出**：`inbox/周扫-YYYY-MM-DD.md`，按 [templates.md](templates.md) §支线投递物 的四节结构写。**空报也要落盘**（明写"本周无变化"），不留空档。

**开轮纪律**：跑之前先 `git log --oneline -3` + `git status --short`（即 §轮次开始 的 pre-flight，此处不重复）——主线程可能正在做同一议题（2026-09-30 实测：第 68/69 轮与首次周扫高度重复）。

**与主线程的分工**：周扫**不写任何权威文件**，产出一律走 `inbox/` 投递物。

> **周扫的独特价值不是"再读一遍论文"，而是"用外部事实核工作空间里的标签"**——2026-09-30 实测：第 69 轮做了深核（读论文正文、问对了 split）却漏了"TOAD 代码其实早已发布"；周扫做的是广扫（查外部状态）却抓到了它。**两者互补，不可互相替代。**

## 轮次开始（pre-flight，2026-09-30 第六十二轮新增）

开工前花几秒做三件事——**收尾检查管"本轮产出对不对"，开轮检查管"本轮是不是基于旧信息"**：

1. **`git log --oneline -5` + `git status --short`**——status 非空说明**有别的会话未提交的活**；log 里最近几条提交动过你本轮要改的文件，说明**别的会话刚收尾过同一批文件**——两者都先问清再动（同一工作树是 last-write-wins，**覆盖无警告**；与 [rules.md](rules.md) §支线协作纪律的硬通道同口径）。
2. **用 Glob `inbox/*.md`（去掉 `cleanup.md`）**——有投递物就**只看主题**判断是否与本轮要改的相关；**相关者先整合，不相关则本轮不动**。（§只读操作禁命令行列目录，故用 Glob 而非 `ls`。）
3. **读 [CURRENT.md](../projects/autonomous-driving/history/CURRENT.md) 的「在改」区**——若别的会话正在改你也要改的文件 → 改期，或只投递（见 [rules.md](rules.md) §支线协作纪律）。

**为什么只在开轮查一次、不随时查**：一轮要写几十个文件，逐个查是纯噪音；而"每次都要记得"这类约定，**正是本工作空间反复证明会失效的那一类**（第 49–54 轮漏了收尾步骤且无警报）→ 所以它由**第 11 项机器检查兜底**（收尾时非 0 即报）；开轮这一步只负责"**早点发现、避免返工**"。

## 轮次收尾（每轮必做，2026-09-23 定）

一轮工作结束前，**同一批事实要同步到所有"手写当前态"的位置**，否则下一轮会读到互相矛盾的数字（历史实例见 [lessons.md](lessons.md) §四）。

> **执行顺序（第七十八轮钉死）**：**9（整合 inbox）→ 1–6（内容同步）→ 7（检查）→ 8（提交）**——先整合再同步，整合出的改动才能进本轮提交；先同步再检查，检查才能看到最终态。
>
> **收尾同步位清单（权威定义，共 9 处）**：① `history/rounds-NN.md` 新卷；② `history.md` 索引行 + 卷数；③ `state.md`（当前阶段 + 待续清单 + **文件头「更新时间」**）；④ **README「最近动态」+「轮次指针表」两处**；⑤ 项目 `index.md`；⑥ 各 `topics/<x>/README.md` 的状态字段；⑦ `project.md`（仅边界变化时）；⑧ **`shared/index.md` + `shared/tools.md` 的当前态**（工具状态/口径变了由本轮同步——第 77 轮起立）；⑨ **`CURRENT.md` 页脚"最近一次填写"**。
> **动了哪个项目，就同步哪个项目的 ①②③⑤⑥⑦；README（④）与 ⑧⑨ 每轮必同步。改具身侧文件 → `embodied-ai/history.md` 必须含本轮条目**（第 55/57/59/60 轮漏过、第 77 轮又漏过一次）。
> 机器兜底：卷数与各类计数 → `check_links.py` 第 9 项登记表；**README 轮次表完整性（最新一卷入表 + 区间无缺口）→ 第 13 项**。

1. `history/rounds-NN.md`：本轮做了什么、更正了什么（**细节只写这里**）
2. `state.md`：阶段、待续清单、判断边界索引（行数与体积都要在预算内）
3. `index.md` 与 `README.md` 的"最近动态"：只留 1–2 行指针，不写结论
4. **各 `topics/<x>/README.md` 的「状态」字段与「产出状态」节**——最易漏（历史实例见 [lessons.md](lessons.md) §四）
5. **`project.md`**：只写定义与边界；**进度一律写成指针**（"以 `state.md` 为准"），不复述易失真的数字
6. **计数类事实先找权威源**：仓库数 → `code/repositories.md`；来源与代码可用性 → `sources.md`；论文与笔记篇数 → 各 `papers.md`。其余文件引用时必须指向它，**历史数字要加"当时 N 个"的限定**，否则会与当前值混淆
   - **同一份"清单"只允许一个权威版本，其余一律只留指针**：凡"扩到 N 种 / 第 N 例"这类随轮次增长的计数，旧位置必须改成指针或加"当时 N 种"限定——**引用可以重复，计数不能**（原始案例见 [lessons.md](lessons.md) §三.7）
7. 复跑检查：**跑 [shared/scripts/check_links.py](../shared/scripts/check_links.py)**——**逐项清单、以及每项的动因一律见脚本 docstring 与内联注释，本文件不重复项清单、不写总数（项号锚点可用）**（三处抄清单漏过两次的教训见 [lessons.md](lessons.md) §四.15）。**判据只有一条：`exit 0` 才算通过**；任一项不过即 `exit 1`，明细打印在输出里。
   - **⚠ 本步必须在第 9 步（整合 inbox）之后跑**：第 11 项度量的是"**待办状态**"（`inbox/` 有待整合即报），**不是"缺陷"**——若先跑本步再整合，第 11 项必然报红，与第 8 步"必须在 `exit 0` 之后提交"直接卡死。**两条出路**：① 把整合放前面（推荐：Glob `inbox/*.md` → 整合 → 跑本步 → 提交）；② 已先跑过本步的，整合后**重跑一次**再提交。
   - **不过怎么办**：先修再提交（第 8 步）；确实修不完的，在提交信息里写明"已知告警：…"。
   - **两条写作约定**（不是"检查的实现"，而是"写文档时要守的规矩"）：① **一篇论文有笔记，就要在它出现的论文表行、脉络或 `repositories.md` 里留一个指针**——否则读论文表的人看不到这些论文有全文笔记；② **拆册后先跑这项**——`§X` 挂错文件**死链检查抓不到**（文件确实存在），**换 basename 拆册尤其要跑**（坑踩过三次，见 [lessons.md](lessons.md) §三.9）。
   - **登记表随内容更新**：脚本里有两张**显式登记表**——「声明计数 vs 权威源」的 `COUNT_RULES` 与「CSV↔md」的 `CSV_ID_PAIRS`。文档措辞改了要同步改登记表；**"声明处没匹配到"也会报出来**，那正是"该更新登记表"的信号。
   - **同一事实的一致性顺手抽查**：跨文件对同一数字/结论的说法——**新写的事实若推翻了旧结论，必须就地标 `⚠ 更正` 并保留原依据**。
8. **提交 git**：**命令本身、身份怎么传、为什么不用 `git add -A`、提交前缀三类、轮次 tag、`.gitignore` 忽略——完整要求见 [rules.md](rules.md) §执行与清理纪律第 9 条（那是「执行与清理纪律」的唯一定义处），本文件不复述**。
   - 本步只记**两条顺序**要求：① **必须在第 7 步 `exit 0` 之后**（检查全绿才提交，否则把坏状态固化进历史）；② **必须在第 9 步整合完 inbox 之后**（否则整合出的改动进不了本次提交）。
   - **⚠ 支线投递提交不受 `exit 0` 门槛约束**：支线的职责就是往 `inbox/` 放投递物 → 第 11 项**必然**报红，**这是它的职责、不是缺陷**——不要因此误判成"规则矛盾"。
   - **提交前自查**：`git status --short` 里**不该出现** `code/repos/` 或 `inbox/scratch/` 下的任何文件——出现即说明 `.gitignore` 漏了。
   - 提交信息写"**改了什么、为什么**"，不要只列文件清单——半年后需要的是"当时为什么这么改"（与 [workspace-design.md](../shared/workspace-design.md) 运行纪律第 7 条「决策留痕」一致）。
9. **整合 inbox 投递物（见 [rules.md](rules.md) §支线协作纪律）**：**直接用 Glob `inbox/*.md`**（投递物的登记表就是 `inbox/` 本身）→ 把投递物里的**事实**整合进对应表 / 脉络 / `state.md`，并在本轮 `rounds-NN.md` 里写明"**整合了哪些投递物**"。
   - **顺序**：本步**应在第 8 步提交之前、并在第 7 步复跑检查之前完成**（否则整合出的改动进不了本次提交，且第 11 项不会归零）；整合产生的改动与该轮改动**同一次提交**。
   - **投递物 ≠ 临时产物**：投递物在 `inbox/` 根（待整合、有意义），临时产物在 `inbox/scratch/`（中间文件、直接被忽略）——**别把投递物当 scratch 删掉**。
   - **投递物里的"事实"要复核再落盘**，不能照抄：支线可能只有单侧证据（虚报实例见 [lessons.md](lessons.md) §四.16）。
   - **归档（三种处置）**：**`inbox/` 只放"待处理"，不放"已处理"**——否则第 11 项检查每轮报同一篇，几轮后就被无视（"永久报警"的宿命见 [lessons.md](lessons.md) §五.20）。

     | 处置 | 动作 |
     |---|---|
     | **采纳** | 整合进表 / 脉络 / `state.md` → 移入 `archive/YYYY-MM-DD-支线交付-<主题>.md` |
     | **否决** | 移入 `archive/` + **在本轮 `rounds-NN.md` 写明否决理由** |
     | **搁置** | 移入 `archive/` + 注明"**搁置，见第 N 轮**" |
   - **归档件要加文件头说明**（整合到哪些文件、由哪一轮整合、下文相对链接按当时位置可能失效），**原样保留、不回改**。
   - **收尾 `CURRENT.md`**：把本轮「在改」区清空 + 页脚改为"最近一次填写：第 N 轮（已收尾）"。
