# AI 工作流

证据等级的定义见 [rules.md](rules.md) §证据等级（**不在此重复**）。

## 文献检索

1. 确认检索范围和关键词；**记录查询式与去重后篇数**（供复核，写进 `raw/` 检索日志）
2. 多源检索（arXiv, OpenAlex, Crossref, 出版社页面）
3. 去重、记录版本关系（同名不同篇、会议版与预印本版要分清）
4. **按质量分档筛选**（T1–T5，口径见 [shared/literature-quality.md](../shared/literature-quality.md)）——**未发表的预印本**用"强团队 +（有代码 或 方法独特）"口径；**已发表**优先看 CCF 评级与引用量
5. 按主题分级（A=直接相关，B=广义相关，C=专题补充，D=待核验）
6. **venue 三渠道并行核验**（见 [rules.md](rules.md) §venue 核验）——`comments` + OpenAlex 按标题 + Crossref 按 DOI；**"Submitted to" ≠ 录用**
7. 输出结构化表格并登记到来源索引
8. **边界外清单要定期复核**：列在"边界外"的条目不是永久排除，团队/venue/代码状态变化时逐条重判（实测 15 条复核里有 9 条应升为正式收录）

## 论文精读（摘要 → 全文）

1. 摘要级只记"作者自己声称什么"，**不记数字**
2. 升全文后：**先核表格数字**（PDF + `pdftotext -layout` 逐格），再读方法节
3. **必须区分受控消融与榜上对比**——同一张表里两行不同方法的差值**不能归因到机制**（实测一处误读：把 Table 1 两行不同方法的 24.2→55.5 当成"换条件带来的收益"，真实受控收益只有 +3.7）
4. 每条关键事实标注 `表号/节号`，便于回查
5. **每篇的结论落到"对本项目意味着什么"**，否则只是读书笔记

## 代码脉络梳理

1. 固定论文版本和代码 commit
2. 识别基线模型（继承关系）
3. 识别引入的模块来源（组合关系）
4. 核验论文核心创新点对应的代码改动（对应关系）
5. 记录可比较条件：输入、输出、监督、评价协议
6. **标注代码核验级别**（L1 逐文件 / L2 仓库存在性 / L3 API+raw 未克隆，见 [rules.md](rules.md) §代码静态检查）
7. **专门找"名字 ≠ 实际"**——已积累七类陷阱：① 配置覆盖链 ② 声明未接线 ③ 零权重 ④ 死引用 ⑤ 被注释关闭 ⑥ 命名与实现语义不符 ⑦ **论文机制落在"评测路径没 import 的版本"里**（实测 GuideFlow：CVF 只在 v8、RFE 只在 v10，而评测 import 的是 v6）
8. **负面结论同等重要**：零代码、机制未发布、权重为 0、数字不可复现，都要写进表与脉络，**不能只记正面发现**

## 脉络梳理（lineage）

产出物：领域层 `direction/lineage.md`、小方向层 `topics/<x>/lineage.md`。模板见 [templates.md](templates.md)。

1. **先表后脉络**：先把论文表（事实）建完，再写脉络（判断）；脉络里只写判断，事实留在表与笔记，不重复
2. **阶段划分要给出分界标志**，不能只按年份切；分期方式本身可能有分歧（不同综述用不同切法），要写明分歧而不是抹平
3. **每条"关键转移"回答三问**：之前是什么、之后是什么、我的判断是什么
4. **未解决问题标注"谁明确提出"与证据等级**，不写成自己的判断
5. **章节末必须有「证据边界」**：哪些是论文自述、哪些经代码核验或实际运行
6. **只给领域整体与研究对象写厚脉络**；借鉴来源写薄脉络（阶段 + 关键节点 + 与研究对象接口的差异）

## Idea 讨论准备（2026-09-23 定）

讨论前的准备材料集中在一份 `ideas/preparation.md`，结构固定为：

1. **研究地图**：这个子方向在做什么（主线 + 横切轴）
2. **可作为设计前提的已验证事实**：每条标证据等级；**与 `judgments.md` 不重复**——此处只留"对设计有约束力"的条目并指向 `judgments.md`
3. **明确未解决的问题**：附"谁明确提出"（P1、P2…编号可被方向引用）
4. **可迁移机制**：独立成 `transfer.md`，本文只放入口指针
5. **潜在方向空间**：每条给出「依据 → 重合风险 → 最小验证实验 → 需要什么 → 停止条件」五要素
6. **比较口径**：讨论前必须先固定的规则（基准划分、输入权限、输出模态、命令维）
7. **需要用户决定或补充的信息**

**纪律**：
- **每条方向必须写"重合风险"**，且要基于代码级核验而非摘要——已多次出现"初判空白、核验后空间变小"（如"约束注入层级选择"）
- **收益量级要横向对齐**：把各机制轴的受控收益放在一起比（实测四条轴都在 +3.7 ~ +6.7，**没有一轴远大于其他轴**），避免把某个方向当成显然更优
- **不自动升级候选 idea 为选定方向**（见下）

## Idea 验证

1. 检查候选 idea 与已有工作的重合
2. 检查数据是否提供所需监督信号
3. 检查环境是否允许验证
4. 估计实验成本和失败回退成本
5. 明确停止条件
6. 不自动升级候选 idea 为选定方向

## 实验

1. 固定环境版本、数据版本、评价协议
2. 记录训练配置、超参、随机种子
3. 区分受控比较与系统级比较
4. 实验失败不等于 idea 错误；记录失败原因和调整建议

## 轮次开始（pre-flight，2026-09-30 第六十二轮新增）

开工前花几秒做三件事——**收尾检查管"本轮产出对不对"，开轮检查管"本轮是不是基于旧信息"**：

1. **`git status --short` 应为空**——非空说明**有别的会话未提交的活**，先问清再动（同一工作树是 last-write-wins，**覆盖无警告**）。
2. **`ls inbox/*.md`（去掉 `cleanup.md`）**——有投递物就**只看主题**判断是否与本轮要改的相关；**相关者先整合，不相关则本轮不动**。
3. **读 [CURRENT.md](../projects/autonomous-driving/history/CURRENT.md) 的「在改」区**——若别的会话正在改你也要改的文件 → 改期，或只投递（见 [rules.md](rules.md) §支线协作纪律）。

**为什么只在开轮查一次、不随时查**：一轮要写几十个文件，逐个查是纯噪音；而"每次都要记得"这类约定，**正是本工作空间反复证明会失效的那一类**（第 49–54 轮漏了收尾步骤且无警报）→ 所以它由**第 11 项机器检查兜底**（收尾时非 0 即报）；开轮这一步只负责"**早点发现、避免返工**"。

## 轮次收尾（每轮必做，2026-09-23 定）

一轮工作结束前，**同一批事实要同步到所有"手写当前态"的位置**，否则下一轮会读到互相矛盾的数字（实测一次抽查就查出 7 处 stale，其中 1 处与事实直接矛盾）：

1. `history/rounds-NN.md`：本轮做了什么、更正了什么（**细节只写这里**）
2. `state.md`：阶段、待续清单、判断边界索引（行数与体积都要在预算内）
3. `index.md` 与 `README.md` 的"最近动态"：只留 1–2 行指针，不写结论
4. **各 `topics/<x>/README.md` 的「状态」字段与「产出状态」节**——最易漏。实测一次抽查发现 VLA 侧停在"两轮 / 18 篇"、世界模型侧停在"三轮 / 9 篇全文"，而实际已是四轮 / 28 篇 / 24 篇
5. **`project.md`**：只写定义与边界；**进度一律写成指针**（"以 `state.md` 为准"），不复述易失真的数字
6. **计数类事实先找权威源**：仓库数 → `code/repositories.md`；来源与代码可用性 → `sources.md`；论文与笔记篇数 → 各 `papers.md`。其余文件引用时必须指向它，**历史数字要加"当时 N 个"的限定**，否则会与当前值混淆
   - **同一份"清单"只允许一个权威版本，其余一律只留指针**（2026-09-24 第三十三轮补）：实测 `judgments.md` 的 **"RL 词义核验"清单**在**三条**里分别写成 **3 / 5 / 9 种**、且全是现在时（第三十三轮统一为九种 + 指针）；另一处"非生成式基线"在**同一条目内**标题写"三种"、正文写"扩到五种"。→ **凡"扩到 N 种 / 第 N 例"这类随轮次增长的计数，旧位置必须改成指针或加"当时 N 种"限定**；这与"引用类"（同一篇论文在多处出现）不同——**引用可以重复，计数不能**
7. 复跑检查：**跑 [shared/scripts/check_links.py](../shared/scripts/check_links.py)**（**十二项**：死链 / `index.md`·`state.md` 行数预算 / **表格单元格数** / **引用可达性** / **章节引用可达性** / **笔记的「对本项目的意义」节** / **小方向 README 的必写 4 节** / **判断条数一致性** / **声明计数 vs 权威源** / **CSV 与 markdown 表的 ID 一致性** / **inbox 待整合** / **文档体积预算**）
   - **文档体积预算（第六十四轮加）**：**任何文档 ≤ 64 KiB**（65536 字节，**Read 工具一次可整读的物理上限**），超限即报并打印"最大者及其占比"。**此前只是人工"看体积"**（第五十八轮审计列为"未机器化的约定"）——而**超限是静默发生的**（加一节就跨过去），后果是"这个文件从此读不整、且无人报错"
   - **inbox 待整合（第六十二轮加）**：`inbox/` 根下的 `.md`（`cleanup.md` 除外）即"待整合投递物"，**非 0 即报**。**为什么必须机器化**：本工作空间自己的历史证明**人工 checklist 会漏**——第 49–54 轮都漏了收尾第 2/3 步，且**没有任何警报**；而此前那十项检查**全是"踩坑之后才补进去的"**。有了这一项，**不整合投递物，第 8 步就提交不干净**（闭环）
   - **表格单元格数这项是 2026-09-24 加的**：一次审计发现表格里有"行少一格"（渲染错位）与"单元格内未转义 `|`"（把一列劈成两列），而此前只查死链与行数，**这类问题从未被发现**
   - **引用可达性这项也是 2026-09-24 加的**：一次审计发现 **19 篇笔记"只被 `sources.md` 引用"**——读论文表的人根本看不到这些论文有全文笔记。**约定：一篇论文有笔记，就要在它出现的论文表行、脉络或 `repositories.md` 里留一个指针**；`raw/` 检索日志豁免（其唯一正当入口就是 `sources.md` 的登记行）
   - **章节引用可达性（原"分册引用归属"，2026-09-24 加、第四十五轮扩）**：**拆册后正文引用没跟着改**，**这类坑已踩三次**——第二十八轮 C003 的 §I–§P 共 52 处、第三十轮 C005 的 §K–§M 共 13 处、**第四十五轮 `papers.md §5–§14` 共 17 处**。**死链检查抓不到**（文件确实存在），只有"章节在哪"能抓。**前两次是"错册"**（`X.md` ↔ `X-2.md` 同 basename），**第三次是"换了 basename"**——`vla/papers.md` 的 §5–§14 拆到了 **`verification.md` / `verification-2.md`**，旧实现只认册对、完全看不见 → 现规则改为：`§X` 不在目标文件即报（在册兄弟里报"错册"，两边都没有报"没有这一节"）。→ **拆册时先跑这项；换 basename 拆册尤其要跑**
   - **笔记的「对本项目的意义」节（第三十一轮加）**：`templates.md` 早把该节定为**必写**，但实测 **47 篇里 4 篇完全没有、5 篇只写成"在脉络"节里的粗体 bullet**，且节名有 **7 种变体** → 读者与 AI 都定位不到。**该节名称固定为 `## 对本项目的意义`**（可加括注），已全部补齐并纳入检查
   - **小方向 README 的必写 4 节（第三十四轮加）**：`templates.md` 声称的"小方向 README 实际写法"实测**只有 2/6 成立**——**研究对象 `diffusion-planner` 与具身侧 3 个都缺节**（研究对象那个反而最薄）。→ 改为**「必写 4 节（本小方向的文件 / 要回答的问题 / 边界 / 产出状态）+ 按需若干」**，6 个 README 全部补齐并纳入检查
   - **判断条数一致性（第四十四轮加）**：`judgments.md` 的 **D 组实际只有 10 条 bullet，而节标题、索引表、`state.md` 索引表都写 11 条**——一条第十七轮的判断（DIVER 的 `num_cmd` 口径）在某轮编辑中被**静默删掉**，**三处声明彼此自洽、所以肉眼与逐项检查都看不出来**。→ 以**实际 bullet 数为唯一权威**，比对① 节标题 `### X. 标题（N 条）`② `judgments.md` 分组索引表的"条数"列（并核对该行"册"列）③ `state.md` 索引表的"条数"列与总条数。**这是"引用可以重复，计数不能"（第 6 条）在机械层面的落地**——凡是声明的计数，都要有机器核对
   - **声明计数 vs 权威源（第四十四轮加，与上一项同批）**：`state.md` 与 `sources.md` 都写"`transfer.md` **16 条**机制"，而 §1 实际只有 **15** 条——**第三十二轮把条数改正为 15 时只改了 `preparation.md` 那处，兄弟引用漏改**。→ 把"N 篇 / N 个 / N 条"这类声明与**文档之外的权威源**（`code/repos/` 目录数、论文表编号数、笔记文件数、章节数据行数）对齐；**规则登记在脚本的 `COUNT_RULES` 里**（机器无法从"16 条机制"这句话推出它数的是哪张表，所以必须显式登记），**两个项目都覆盖**。**代价与纪律**：文档措辞改了要同步更新登记表——**"声明处没匹配到"也报出来**，那正是"该更新登记表"的信号
   - **CSV 与 markdown 表的 ID 一致性（第四十六轮加）**：工作空间约定"**双表示时 CSV 是权威源**"，但"谁是权威"只在两者一致时才有意义——**一旦漂移，按 md 读的人与按 CSV 检索的人会看到两个不同的集合，而且两边都"看起来对"**；死链、计数、章节三类检查**都管不到**。→ 对每一对 `<x>.csv` + `<x>.md`，两边出现的 ID 集合必须**完全相同**（双向都报）。**实测 4 对全部一致**（45 / 34 / 15 / 28）→ 本项是**把已有的正确状态锁住**。**注意扫"全单元格"而非"ID 列"**：各 CSV 列布局不同（`e2e_ad_surveys` 的 ID 在第 1 列、表头还是小写 `id`），且**待核验 / 边界外**的条目在 CSV 里是"段标题行 + 别的列"，只扫 ID 列会漏
   - **同一事实的一致性也要顺手抽查**：跨文件对同一数字/结论的说法（第二十八轮这样查出 8 处冲突，含"去掉世界模型"却用"加上"的箭头方向）——**新写的事实若推翻了旧结论，必须就地标 `⚠ 更正` 并保留原依据**
8. **提交 git（第四十八轮新增，2026-09-28 用户批准；第六十二轮改 `add` 方式）**：`git add -u && git add <本轮新增的文件路径> && git -c user.name=verse -c user.email=verse@localhost commit -m "第 N 轮：…"`（**不写 `cd`**——Shell 工具的 `cwd` 默认就是工作空间，见 [rules.md](rules.md) 纪律第 6 条）
   - **⚠ 不再用 `git add -A`（第六十二轮改）**：`-A` 隐含假设"**工作区里所有东西都是我的**"——**这个假设在单会话下成立，有了支线就不成立**：主线收尾 `-A` 会**静默扫走支线未提交的半成品**（同一工作树是 last-write-wins，不是 git merge，**没有任何警告**）。改为 **`git add -u`（只管已跟踪文件的改动）+ 显式列出本轮新增文件**。
   - **提交信息前缀规范为三类**（可机器区分主线与支线）：`第 N 轮：<一句话>`（主线轮次）/ `支线投递：<主题>`（支线投递）/ `工具：<主题>`（与轮次无关的脚本、凭据、工具文档）。
   - **轮次打 annotated tag**（第六十二轮加，成本≈0）：`git tag -a round-N -m "<一句话>"`——让正文里"见第 N 轮"能落到 `git show round-N`，`git log round-59..round-60` 直接看一轮改了什么。
   - **为什么放在第 7 步之后**：检查全绿才提交，否则把坏状态固化进历史。**若第 7 步有未修完的告警，先修再提交**；确实修不完的，在提交信息里写明"已知告警：…"
   - **提交信息内容**：首行 `第 N 轮：<一句话>`；正文写**改了什么、为什么**，并列出本轮产出的文件。**不要只写文件清单**——半年后需要的是"当时为什么这么改"（与 `workspace-design.md` 运行纪律第 7 条「决策留痕」一致）
   - **身份用 `-c` 传，不写任何 git config**（本机无 git 身份配置；`verse <verse@localhost>` 是默认值，要改就改这两个 `-c` 参数）
   - **`.gitignore` 的三条忽略**：`projects/*/code/repos/`（1.6 GB 第三方快照）、`inbox/scratch/`（临时根）、`.trae/`（IDE 产物）——**新增临时目录时同步检查是否也会被提交**
   - **提交前自查**：`git status --short` 里**不该出现 `code/repos/` 或 `inbox/scratch/` 下的任何文件**；出现即说明 `.gitignore` 漏了
   - **这与纪律第 8 条的备份并存**：git 是兜底（可 `git diff` 复查、`git checkout` 回滚），第 8 条的 `cp` 备份防的是"**尚未提交的工作**在会话中途丢失"——两者不互相替代
9. **整合 inbox 投递物（2026-09-30 新增，第六十一轮补强，见 [rules.md](rules.md) §支线协作纪律）**：先看 **[CURRENT.md](../projects/autonomous-driving/history/CURRENT.md) 的「待整合投递」区**（支线登记过），再 `ls inbox/` 兜底 → 把投递物里的**事实**整合进对应表 / 脉络 / `state.md`，并在本轮 `rounds-NN.md` 里写明"**整合了哪些投递物**"。
   - **顺序**：本步**应在第 8 步提交之前完成**（否则整合出的改动进不了本次提交）；整合产生的改动与该轮改动**同一次提交**。
   - **投递物 ≠ 临时产物**：投递物在 `inbox/` 根（待整合、有意义），临时产物在 `inbox/scratch/`（中间文件、直接被忽略）——**别把投递物当 scratch 删掉**。
   - **投递物里的"事实"要复核再落盘**，不能照抄：支线可能只有单侧证据（本次实测一处——投递物称"已写进 `tools.md`"，实际 `tools.md` 里没有，且旧文字与新证据相反）。
   - **归档（第六十二轮扩为三种处置）**：**`inbox/` 只放"待处理"，不放"已处理"**——否则**第 11 项检查每轮报同一篇，几轮后就被无视**（所有"永久报警"的检查都是这个宿命）。
