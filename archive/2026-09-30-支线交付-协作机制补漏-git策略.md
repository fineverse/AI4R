```
--- inbox 待整合 ---
```

这样第 7 步（跑检查）+ 第 8 步（提交）就形成闭环：**不整合，提交就不干净**。这才是"自动"——主线不需要记得，检查会把它推到面前。

## 三、补第一个检查点：开轮粗筛

现在只有收尾一个检查点。但主线一轮很长，**若投递物与"本轮正在改的东西"相关，等到收尾才发现 = 主线已基于旧信息做完判断，只能返工。**

在开轮 pre-flight 里加一步（那个点上本来就要确认工作区干净，边际成本为零）：

```bash
ls inbox/*.md 2>/dev/null | grep -v cleanup.md
```

- 有 → **只看主题**，与本轮要改的相关就先整合；不相关则本轮不动
- 没有 → 直接开工

**为什么不在轮内随时查**：主线一轮要写几十个文件，逐个查是纯噪音；而且"每次都要记得"这类约定，正是本工作空间反复证明会失效的那一类。

**建议的规则文字**（新增「轮次开始」一节，置于 §轮次收尾 之前）：

> **轮次开始**：先做 pre-flight——① `git status --short` 应为空（非空说明有支线未提交的活，先问清再动）；② `ls inbox/*.md`，若有投递物则**只看主题**判断是否与本轮相关，相关者先整合。

## 四、inbox 只放待处理

第 9 步只写了"采纳 → 移入 `archive/`"，**否决与搁置没写**——而它们同样必须移出，否则检查每轮都报同一篇，几轮后这条检查就会被无视（所有"永久报警"的检查都是这个宿命）。

| 处置 | 动作 |
|---|---|
| **采纳** | 整合进表/脉络 → 移入 `archive/` |
| **否决** | 移入 `archive/` + 在 `rounds-NN.md` 写明否决理由 |
| **搁置** | 移入 `archive/` + 注明"搁置，见第 N 轮" |

> **原则：`inbox/` 只放"待处理"，不放"已处理"。** 这样"待整合 N 篇"才有信号意义——非 0 就是真有活没干完。

## 五、放宽：支线可**新建** `shared/` 下的文件

现规则第 1 条是"不直接改 `shared/` 与项目文件"（全禁）。建议放宽为：

> **支线可以"新建"，不能"修改"。**

依据是一条硬事实：

- **新建** = 目标路径不存在 = **没有任何人在写它** → 零竞争
- **修改** = 目标已存在 = **主线随时可能也在改** → **静默覆盖**

关于"静默覆盖"要说明白：**同一个工作树里，两个会话改同一文件不是 git merge 冲突，是 last-write-wins。** 支线写完、主线再写回它手上的旧版本，**支线的改动就没了，且没有任何警告**。这比 merge 冲突危险得多——merge 冲突至少会被看到。

具体：支线可新建 `shared/` 下的**脚本 / 凭据文件 / 工具文档**；**已存在的文件一律投递**。

判定极简：

```bash
git ls-files --error-unmatch <path> 2>/dev/null && echo "已存在 → 投递" || echo "新建 → 可写"
```

**为什么值得放宽**：否则支线写个脚本，只能把源码塞进 markdown 投递物、再由主线"抄"出来——**而"抄"正是引入错误的新渠道**。第 60 轮刚实测过这类问题（`workflows.md` 第 9 步现已写明"投递物里的事实要复核再落盘"），脚本正文比事实更容易抄错。

**代价**：支线不能改自己脚本的 bug（也得投递）。我认这个摩擦——**摩擦看得见，静默丢数据看不见**。

## 六、git 策略（5 条，附现状实测）

现状：单分支 `master`、**无远端**、无身份配置（靠 `-c` 内联）、每轮 `git add -A` 一次提交、25 次提交。

**① `-A` 改显式路径（最要紧）**

`git add -A` 隐含假设"工作区里所有东西都是我的"——**这个假设在单会话下成立，加支线后不成立**。主线收尾 `-A` 会扫走支线未提交的半成品，**且无警告**（与第五项的静默覆盖同类）。

改成只列本轮产出的路径；或 `git add -u`（已跟踪文件的改动）+ 显式列新文件。

**② 前缀规范成三类**

| 前缀 | 用于 |
|---|---|
| `第 N 轮：<一句话>` | 主线轮次（规则已规定） |
| `支线投递：<主题>` | 支线投递 |
| `工具：<主题>` | 与轮次无关的工具/凭据/脚本 |

现状实测三种混用：`第 N 轮：` / `docs: `（另一会话 8 次）/ `支线投递：`（1 次）。规范后可机器区分主线与支线。

**③ 加私有远端——收益/成本比最高的一条**

25 轮工作目前**只在一块盘上**。仓库很小（`.git` 约 2.2 MB，`code/repos/` 已被忽略），代理已通，GitHub 私有仓库可直接用。

**④ 轮次打 annotated tag（可选，几乎零成本）**

```bash
git tag -a round-60 -m "<一句话>"
```

让正文里"见第 N 轮"能落到 `git show round-60`；`git log round-59..round-60` 直接看一轮改了什么。

**⑤ 开轮 pre-flight 要求工作区干净**（与第三项的 ①② 同一动作，不重复）

## 七、明确**不推荐** worktree + 分支（附理由）

`git worktree` 看上去是并行会话的正解（独立目录、零覆盖、原生合并），**但本场景不合适**：

- 分支/worktree 的合并是**机械合并**——两边改同一文件的不同位置，git 能自动合
- 而本工作空间的设计**明确说"同一张表的改动不硬合"**——改表的判断需要主线手上的证据链，机械合会写出自相矛盾的表格

**worktree 解决的是"能自动合的情况"；本场景恰恰是"不能自动合、需要语义整合"。** 所以投递模型比分支模型更贴合，不该上 worktree。
