## 二、待安装的规则

### 2.1 `CURRENT.md` 成了新的多写者——唯一写入点违反本规则自身原则

第六十六轮为消除「§一.1 与 §二.7 打架」，给 `CURRENT.md` 的「待整合投递」区开了**唯一例外**（只属支线）。但该区在**单个文件**里，两条支线同时登记即 last-write-wins：

```
支线甲 读 CURRENT.md（版本 A）
支线乙 读 CURRENT.md（版本 A）
甲 追加自己一行 → 写回（A + 甲）
乙 追加自己一行 → 写回（A + 乙）   ← 甲的行没了
```

**这正是本机制要消灭的覆盖风险，出现在唯一被豁免的那个文件上。**

- **严重性：中低。** 有机器兜底——第 11 项检查仍会在 `inbox/` 看到投递物，退化为"到收尾才发现"（通道 A 失效，通道 B + 机器接住），**不会真丢**。
- **但**通道 A 存在的意义就是"避免返工"，此冲突恰好打掉它**唯一的写入点**。
- **可选修法**（择一）：

  | | 修法 | 代价 |
  |---|---|---|
  | **(a)** | 支线**不写** `CURRENT.md`，发现职责全交机器检查；该文件降级为主线程单方面声明 | 通道 A 少一层"支线登记"，但回归单写者 |
  | (b) | 该区改为"每篇投递物各写各的文件"（如 `inbox/.registry/<slug>`） | 新增一个目录与约定 |
  | (c) | 保持现状，但在规则里**明示这是已知窄风险** | 不解决，只记录 |

  **支线倾向 (a)**：它把 `CURRENT.md` 恢复为**单写者**，与本机制"**减少写者优于协调写者**"的主线一致——多写者再配协调机制，等于把刚拆掉的复杂度重新装回来。

### 2.2 规则 4 的理由不完整——它是"覆盖无闸"的唯一补救

§一.4 现写的理由是"避免被主线程收尾的提交扫入"。**漏了更重要的一条**：

> 支线投递后立即提交 → 支线版本**进入 git** → 即使后来被覆盖，`git log -p <file>` 也能取回。

**这是 §三.10 恢复程序的前提。** 没有它，恢复程序对"未提交即被覆盖"的内容无能为力。

建议补上这句——因为"覆盖无闸"是本机制要防的核心风险，而规则 4 是它**唯一**的补救手段，**理由写全才不会被将来的人当成可选步骤**。

### 2.3 规则 4「只含 inbox 文件」与第六十六轮的例外不同步

§一.4 要求支线的提交"**只含 inbox 文件**"；但第六十六轮的例外允许支线登记 `CURRENT.md`——**登记后就不止 inbox 文件了**。

本篇即实例：提交同时含 `inbox/2026-09-30-机制复核与残留不一致.md` 与 `projects/autonomous-driving/history/CURRENT.md`。

建议 §一.4 改为"**只含本支线自己的文件**（inbox 投递物 + `CURRENT.md` 的「待整合投递」区）"，与例外保持一致。
