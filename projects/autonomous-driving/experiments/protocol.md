# NAVSIM v2 navhard：DiffusionDrive 候选池与选优损失测量协议

更新时间：2026-09-28  
状态：**预注册草案，尚未运行**。研究方向尚未正式立项；本协议只定义路线 B 的第一阶段纯推理测量，不预设训练方案或结果。**第五十四轮重构测量层级**：完整政策 EPDMS 与 Stage-1 候选诊断分开。

## 1. 研究问题与决策用途

在固定 NAVSIM / devkit 评价口径下，DiffusionDrive 的原始多轨迹候选池在 navhard 上有多大质量上限？固定取第 0 条候选与现有选优输出之间有多大地板 gap？将候选数从 20 增至 100 是否提高池子天花板？

本阶段用于判断方向 B 是否值得进入 scorer 训练：若扩大候选池后的天花板仍无实质提升，停止 B 并转评方向 A；若池子有提升空间，再设计在线可得监督信号的选优器。这里只做测量，不据此声称新颖性或 SOTA。

## 3. 测量层级：完整政策分与候选诊断分分开

第四十九轮草案把四项测量并列，但 NAVSIM v2 EPDMS 包含 Stage-1 / Stage-2；Stage-2 的跟进场景权重以该政策 Stage-1 的终点为中心。因此先区分完整政策运行与候选池诊断量。

1. **已发布选优输出**：checkpoint / agent 当前提交轨迹的 EPDMS，作为运行基线。
2. **无选择地板**：固定取候选索引 0，不按任何 GT 或评测分数挑选；记录 EPDMS。
3. **Stage-1 候选质量分布**：保存全部候选，报告明确标注的 Stage-1 指标、top-1 与 proposal-level oracle；不代表完整两阶段 EPDMS。
4. **扩池诊断**：确认 checkpoint 支持多次采样、候选索引可对齐、随机种子可控后，比较 20 与 100 条池子的 Stage-1 诊断；改变生成分布或预算时标为探索性结果。

若要报告完整 EPDMS 的候选 oracle，必须先核清每个 Stage-1 候选对应的 Stage-2 分支、跟进场景复用规则和最终聚合顺序。在此之前不计算 C_N − S 作为 EPDMS 选优损失。

### 指标定义

- `F`（index-0 policy）：固定提交候选 0、完整运行两阶段后的官方 EPDMS。
- `S`（published policy）：已发布选优策略、完整运行两阶段后的官方 EPDMS。
- `C_N`（ceiling@N）：**诊断量，不直接等同于官方 EPDMS**。先对每个候选按完整评测路径得到场景级结果，再记录候选中的最大场景级结果；只有在固定候选集合、固定阶段跟进场景和固定聚合顺序下，才可将这些结果汇总。不得把“先逐场景取最大、再套官方两阶段聚合”称为官方 EPDMS。
- `S − F`：两个完整政策的描述性分差，不自动等同于因果增益。
- `P_N`（proposal diagnostic）：N 个 Stage-1 候选的诊断指标；具体评分与归一化须按 devkit 实现预先固定。
- `C_N`（full-pipeline oracle）：暂不定义为汇总分；待 Stage-2 分支和候选级聚合映射代码核清后再补充协议。

以上差值均从**同一评测路径产生的场景级结果**计算；同时保存逐场景原始值与失败项，不能只保存汇总分。NAVSIM 的 EP 是候选批内相对量，且 EPDMS 两阶段权重以方法终点为中心，因此候选集合改变时，场景分数和聚合权重都可能改变。`C_N` 使用评价真值，因此明确标为 oracle 诊断量，不属于合法推理性能；若无法为每个候选保留完整两阶段评测上下文，则只报告 proposal-level 上界，不报告伪造的 EPDMS ceiling。

## 4. 执行顺序与记录

1. 获取并校验 checkpoint、navhard 数据与 devkit；记录来源、文件校验和、代码 commit、依赖版本及评分配置。
2. 用少量场景验证 agent 契约、候选张量、索引 0、随机性、轨迹时域与坐标系。
3. 核对 Stage-1 到 Stage-2 的评测实现，明确完整政策的场景权重与聚合；分别运行 published policy 和 index-0 policy。
4. 独立保存 Stage-1 候选诊断；确认 100 候选机制、资源成本与时延后，再决定是否扩池。
5. 结果文件放 `experiments/results/<run_id>/`；运行配置与摘要写入 `experiments/records/<run_id>.md`。原始逐场景结果保留，报告汇总值和按场景 bootstrap 置信区间；若实现成本不允许 bootstrap，须注明。

每个 run 记录：运行 ID / 日期、代码 commit、devkit commit、checkpoint 校验和、数据版本与场景数、配置、种子、硬件、四项测量、运行时延、失败数、偏离协议事项、原始结果路径。不得把静态代码判断写成运行结果。

## 5. 判定规则

- **继续方向 B**：完整政策 `S − F` 可稳定复现，且 Stage-1 候选诊断显示有可用质量空间；之后再设计不依赖评价 GT 的在线选优信号。
- **转方向 A / 暂停 B**：index-0 与 published policy 的差异无法复现，或 Stage-1 候选池几乎没有质量空间。
- **不作结论**：checkpoint、devkit、数据 split 不一致；agent 读取了 GT；候选索引或 Stage-2 分支语义不明；评分配置不匹配；或失败场景被静默排除。先修协议再重跑。

本草案不设臆造的绝对分数阈值。拿到小样本重复运行后，用观测到的运行波动确定“清楚大于噪声”的判据，并在全量运行前写回本协议。
