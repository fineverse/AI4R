# 第六十一轮（2026-09-30）· 完善并行会话的同步机制

**动因**：用户要求"查看支线投递的内容，完善一下"——第六十轮把支线提案的 §2 原样装进了工作空间，本轮**检查这套机制本身够不够**。

**诊断（读支线投递物 + 已装的规则，找出四个漏洞）**：

| # | 漏洞 | 后果 |
|---|---|---|
| 1 | **只有一条通道**：规则只要求"动手前先读 `CURRENT.md`" | `CURRENT.md` **可能没被写、可能过期、可能是别的会话忘了清** → **单点失效**。投递物自己也承认"当时的支线**连 `git log` 都没看**"，而新规则并没有把"看 `git log`"写进去 |
| 2 | **方向是单向的**：只规定"主线程写在改什么、支线去读" | **主线程无从知道支线投递了没有**——只能靠翻 `inbox/`（第六十轮实际就是这么发现的） |
| 3 | **冲突已经发生时没有程序** | 覆盖已发生（`rounds-57` / `rounds-55`）靠临场反应恢复；**程序没有成文**，下次还要重新想 |
| 4 | **投递物没有结构** | 支线与主线程之间**没有稳定接口**——第六十轮就撞到"投递物称某事实已写进 `tools.md`，实际没有且旧文字与新证据相反"；归档命名与归档说明也是我临场自创的 |

## 补强（四处，全部落在活文档上）

### 1. `ai/rules.md` §支线协作纪律——重写为「分工 + 同步机制 + 冲突处置 + 归宿」四节（12 条）

- **通道 A（软）**：`projects/<项目>/history/CURRENT.md` —— 主线程写「在改」、**支线投递后在「待整合投递」区登记一行**（堵漏洞 2）。
- **通道 B（硬，新增）**：**`git log --oneline -5` + `git status --short`，任何会话写文件前必跑**。判据：目标文件在最近几条提交里被动过、或工作区有未提交改动落在它上面 → **停手投递，不覆盖**（堵漏洞 1）。
- **恢复程序（新增）**：`git log --oneline` 找覆盖前提交 → `git checkout <commit> -- <file>`（未提交的用 `git checkout HEAD -- <file>`）→ **比对体积/`diff` 确认取回的是原文件** → 写进该轮轮次记录；并立"**恢复优先于续写**"（堵漏洞 3）。
- **投递物结构**：必须按 `templates.md` §支线投递物（堵漏洞 4）。
- **归档约定（新增）**：`archive/YYYY-MM-DD-支线交付-<主题>.md` + **文件头加归档说明**，**原样保留不回改**。

### 2. `ai/templates.md`——新增「§支线投递物」模板

给出可直接套用的四节结构（**一、已提交的产出 / 二、待主线程安装的规则（可直接粘贴）/ 三、待主线程处理的遗留 / 四、本投递物的证据等级**）+ 五条写法要求。其中两条是**本轮从事故里提炼**的：

- **§二 要给"可直接粘贴的成品"，不要只写意图**（只写意图 = 让主线程重做一遍）。
- **§三 的"已完成"必须能被独立复核**，且**不占轮次号要显著标出**（第 57 轮的重号事故就源于没这条）。

### 3. `ai/workflows.md` §轮次收尾 第 9 步——补三条

先看 `CURRENT.md` 的「待整合投递」区、再 `ls inbox/` 兜底；归档命名 + 归档说明；**整合完清空该区**。

### 4. `history/CURRENT.md`——从"只有「在改」"扩为两个区

「在改（主线程本轮）」+「**待整合投递（支线登记）**」，并把**通道 A/B 的说明写在文件头**（读这个文件的人立刻知道还有硬通道）。

**验证**：`check_links.py` **十项全绿**（死链 0）。

**方法论**：第六十轮是"**把别人的提案装进去**"，本轮是"**检查这套机制自己会不会失效**"。差别在于问了一句：**"如果对方没按约定做，机制还成立吗？"**——原方案要求"先读 `CURRENT.md`"，而**这个文件本身就是可选的、可忘的**，于是机制在对方违约时**静默失效**（正是本次事故的形态）。所以补了**不依赖对方的硬通道（`git log` / `git status`）**：**软通道提高效率，硬通道保证正确**，两者都要有。
