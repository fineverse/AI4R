# 第六十二轮（2026-09-30）· 整合支线第二篇：把"整合投递物"从 checklist 变成机器检查

**动因**：用户要求"查看支线投递的内容，完善一下"。支线在第六十一轮工作期间投递了**第二篇**（`80c90f6`，**只含一个 inbox 文件——纪律生效：没有覆盖任何主线程文件**），共 5 项，与本轮主题互补。用户对 5 项**全部采纳**（唯一未做的"加私有远端"需用户提供仓库）。

## 一、最关键的一项：`check_links.py` 新增第 11 项「inbox 待整合」

**支线的论证**（本轮复核认可）：本工作空间**自己的历史证明人工 checklist 会漏**——[rounds-57.md](rounds-57.md) 自己写过"第 49–54 轮都漏了收尾第 2/3 步"，**且没有任何警报**；而 `check_links.py` 现有**十项检查全是"踩坑之后才补进去的"**。

- **规则**：`inbox/` **根**下的 `.md`（`cleanup.md` 除外）即"待整合投递物"，**非 0 即报、并让脚本 `exit 1`**。**不查子目录**（`inbox/scratch/` 是临时产物根）。
- **闭环**：第 7 步跑检查 + 第 8 步提交 → **不整合投递物，提交就不干净**。
- **验证（正反各一次，本轮实跑）**：**正**——投递物尚在 `inbox/` 时，输出"待整合投递物: **1 篇** + 路径"，`exit=1`；**反**——整合并移入 `archive/` 后，输出"**0 篇**"，`exit=0`。

## 三、明确不推荐的（支线已给理由，本轮采信）

**不上 `git worktree` + 分支**：分支/worktree 的合并是**机械合并**（两边改同一文件不同位置，git 能自动合），而本工作空间的规则明确写着"**同一张表的改动不硬合**"——改表的判断需要主线程手上的证据链，机械合会写出自相矛盾的表格。**worktree 解决的是"能自动合"的情况；本场景恰恰是"不能自动合、需要语义整合"**。

## 四、本轮未做

- **加私有远端**（支线建议的 git 策略第 ③ 条，收益/成本比最高的一条）：**需用户提供 GitHub 私有仓库**（当前 25+ 轮工作只在一块盘上，`.git` 约 2.2 MB，`code/repos/` 已忽略）。
- 第 60 轮遗留的 `/tmp/ai4r-*` 清理：**仍未执行**（见 [state.md](../state.md) 待续第 20 项）。
