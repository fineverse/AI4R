# 第六十六轮（2026-09-30）· 机制实测：硬机制全通，查出规则自相矛盾 + 一处虚报

**动因**：用户要求"看看投递物，检查之前设计的机制能否正常运行"。检查中发现 `inbox/` 有**第三篇投递**（`b0d49f9 支线投递：沙箱权限边界 + 覆盖风险`），于是把第 60–62 轮设计的机制**逐件实测**，再将结论与投递物一起处理（用户："你自己决定就好，你修好了我再让其他线程投递"）。

## 一、机制逐件实测

| 机制件 | 设计意图 | 实测 |
|---|---|---|
| **机器兜底**：`check_links` 的「inbox 待整合」 | 不整合就提交不干净 | ✅ 报"待整合投递物: **1 篇** + 路径"，**`exit 1`** |
| **通道 B**：`git log` / `git status` | 不依赖对方的硬通道 | ✅ `git log` 顶部即 `b0d49f9 支线投递：…`；工作区干净 → **支线按纪律提交、且只含 inbox** |
| **孤儿豁免** `inbox/` | 投递物整合前不该有入链 | ✅ "已豁免 inbox/ 投递物 **1 篇**"，孤儿仍为 0 |
| **开轮 pre-flight** | 早点发现、避免返工 | ✅ 用只读工具当场发现 |
| **恢复程序前提** | 覆盖后可取回 | ✅ `round-62..65` tag 齐备，`git checkout <commit> -- <file>` 可用 |
| **通道 A**：`CURRENT.md` 登记 | 主线程事先知道有投递 | ❌ **未登记**（该区仍写"无"） |

**总判**：**硬机制（机器检查 + git 通道）全通，且把软规则的失效接住了**——这正是第 61 轮定的"**软通道提高效率、硬通道保证正确**"。

## 二、查出问题 ①：规则**自相矛盾**（不是支线违规）

- 第六十一轮写 §二.7：**支线要在 `CURRENT.md` 的「待整合投递」区登记**；
- 第六十二轮写 §一.1：**支线"已存在的一切文件一律投递"**——`CURRENT.md` 早就存在 → **不能改**。

→ **两条直接打架**，支线守了后者（不登记），**通道 A 因此失效**。**责任在规则，不在支线**。

**修法**：给 §一.1 加**唯一例外**——`CURRENT.md` 的「待整合投递」区（该区**只属支线**：主线程只清空、不填），支线可在那里**追加一行**。

**教训（写进被修处）**：**规则之间也要查"会不会互相打架"**，不能只查每条自身对不对——这与第 63 轮"同一事实写两处会漂"是同一族问题，只是对象从"事实"变成了"规则"。
