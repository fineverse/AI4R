## 1. 研究地图：这个子方向在做什么

**一句话定位**：扩散规划器 = 用生成模型（扩散 / 流匹配 / 扩散桥）直接产出驾驶轨迹分布，替代"回归一条轨迹 + 规则后处理"。

三条主线（按生成机制分）：

| 主线 | 代表 | 起点先验 | 步数 | 现状 |
|---|---|---|---|---|
| 截断扩散 + 锚点 | DiffusionDrive（DP-A02）、DiffusionDriveV2（DP-A03）、AnchDrive、DriveAnchor | 锚点高斯 / 轨迹词表 | 2 步 | 工程最成熟、NAVSIM 上被反复对比 |
| 纯噪声 + 引导 | Diffusion Planner（DP-A01，nuPlan 闭环） | 纯高斯 | 多步 + DPM-Solver | 闭环 nuPlan 路线，靠 classifier guidance 调风格 |
| 流匹配 / 一步生成 | GoalFlow（DP-A09）、MeanFuser（DP-A14）、WAM-Flow（DP-A13）、FlowDrive | 纯高斯 / 高斯混合噪声 / 离散 token | 1–5 步 | 2025–2026 的主流竞争路线，速度优势明显 |

三条横切轴（按"创新位置"分，这比按模型分更有用）：

1. **约束注入位置**：事后优化 → 软奖励（RL）→ 生成过程内硬约束。
2. **条件来源**：场景 BEV/矢量化 → 目标点 → 语言推理 → 未来潜状态。
3. **选优机制**：轨迹评分器 / 模式选择器（selector）越来越关键，也逐渐成为瓶颈。

### 2.1 生成机制侧

| # | 设计前提 | 量化依据 | 对设计的约束 |
|---|---|---|---|
| S1 | **实时性可由少步化解决** | DiffusionDrive 2 步 / 4090 上 45 FPS；GoalFlow 1 步 10.4 ms（PDMS 88.9）、5 步 49.0 ms（90.3）；MeanFuser 1 步 59 FPS | **"慢"不是生成式规划的固有缺陷**；这些数字跨 backbone 与输入权限，**不可横比** |
| S2 | **起点先验的"质量"本身带来收益，不一定是"离散化"** | MeanFuser 用连续高斯混合噪声（GMN）+ MeanFlow **超过**锚点词表方案 | 做"锚点 vs 纯噪声"对照时，**要拆开"离散化"与"先验质量"两个变量** |
| S3 | **换生成机制有约 5 PDMS 的受控收益** | SpanVLA 把 L1 回归头换成 flow matching：85.1 → 90.3（**+5.2**，同一 VLM 编码下只换动作头），代价 0.02 s → 0.08 s | **收益与延迟必须一起报**——这不是免费午餐 |
| S4 | **"生成式"有两条互不相干的路线** | ① 隐变量生成（**GenAD**：32 维对角高斯 + spatial GRU + 解析 KL，非扩散、无词表）② 轨迹词表 / 扩散 | 做"生成式 vs 非生成式"对照**必须把 GenAD 作为独立的第四类** |
| S5 | **"必须靠锚点/词表"已被证伪两次** | HDP（DiT 一次去噪出整条轨迹）；**Flow Planner**（7 个 action token = 随机噪声 + 4 步 midpoint ODE 后 `average`，直取 `outputs[0,0]`，**全仓无任何 `.npy`/`.pkl`**） | 两个生态各被证伪一次；**Flow Planner 是"纯生成、无选择"的最干净基线**，做"生成 vs 选择"对照时是**必需对照组** |

### 2.2 选择机制侧

| # | 设计前提 | 量化依据 | 对设计的约束 |
|---|---|---|---|
| S6 | **"生成 → 选择"的最后一步各方法都不同** | scorer 选一条（DiffusionDrive）/ 词表与扩散输出**拼池**后选优（DDV2，**输出可以不是扩散样本**）/ **128 条采样取均值**（GoalFlow）/ cls argmax + 规则扣分（SparseDrive） | **"均值化"必须作为独立一类**，与"选优"不可混谈 |
| S7 | **"非生成式基线"是五类不同系统，不是一类** | ① 单模回归（UniAD / VAD v1 / TransFuser）② 锚点+回归（SparseDrive，18 = 3 命令 × 6 模态）③ 离散词表+分类（VADv2 的 4096 词表，**回归分支被乘 0 丢弃**）④ **采样+规则代价选优**（**ST-P3**：2400/1800 条候选 + 7 项代价 + `topk`）⑤ 按命令切分支（LBC / CIL，`select_branch` **无打分**） | 拿 UniAD 当代表会**低估基线**；**④ 与"扩散 + scorer 选优"结构最接近，最容易被误标成"生成式"** |
| S8 | **选优依据的信号有三种，且三家都在选择环节用 GT** | 学到的奖励模型（**WoTE**：256 候选 → 世界模型预测未来 BEV → imitation softmax + 5 个 PDM 子指标）/ 规则 cost volume（**Drive-OccWorld**）/ 世界模型自身损失（**World4Drive**，但模态分配用 GT 的 FDE） | **"推理期不依赖 GT 也能选对"仍是空白** |
| S9 | **选优器在困难基准上的权重被低估** | **navhard 的高分靠 scorer**——DriveFuture 55.5（**其同文不含 scorer 只有 34.6**，即 scorer ≈ +20；**⚠ 这个 +20 有三个成立条件：基线无选择环节 / 候选池 100 条 / 同文受控——见 [sota-plan.md §7.2](sota-plan.md)，20 锚点池拿不到**）；**navtest 的高分也靠 scorer**——WoTE 88.3/87.1（**注意：WoTE 是 navtest，不是 navhard**，此处此前混记） | 做困难基准实验时**必须把选优器当独立变量**，否则无法归因 |
| S10 | **"选优器是新的瓶颈"已被原作者自述** | DiffusionDriveV2 全文自述依赖 selector、参数少、OOD 下易失效；DP-A34 指出强规划器的候选集中在安全模式，边界附近监督不足 | 方向 B 的依据；但**"选优器"在代码层已有三种现成实现可对照**（S8） |

### 2.3 约束与可行性侧

| # | 设计前提 | 量化依据 | 对设计的约束 |
|---|---|---|---|
| S11 | **可行性违规是可测的现状，不是假想问题** | DiffusionDrive 曲率违规 **8.59%**；ReCogDrive 8.05%（普通 GRPO **15.5%**）；FeaXDrive 做到 **0.88%**；可行驶区违规 5.06% → 2.54% | **违规率是方法相关指标**（判据 = 核平滑 ksize=5 → 弧长参数化 → 变步长中心差分 → 两端点补 0）→ **跨论文不可比，本项目必须自定义并公开判据** |
| S12 | **"快"和"有硬约束"目前不可兼得** | 实时方案（45 / 59 FPS）**没有硬约束**；有**约束**的方案很慢——**硬约束** PC-Diffuser **约 2 fps**（5× 延迟），**软引导** GuideFlow **3.6 FPS**（DP-A12 **无 QP/投影证书**，见本文件 §2b 的四立场表） | **"实时 + 硬约束"这个交集无人做到**——这是方向 A 的核心，也是它唯一还站得住的空白。**⚠ 更正（第三十轮）**：原把 GuideFlow 归入"有硬约束的方案"，与 §2b 对它的分类（**生成内软引导，非硬约束**）自相矛盾 |
| S13 | **约束位置存在正面对立（两篇全文互斥主张）** | PC-Diffuser 把 CBF-QP 放进**每个去噪步**（有证书，CR 100% → 10.29%）；G2SD 用理论论证"去噪内注入安全力会造成**流形破裂**"，主张前移到图规划层 | 两派**从未在同一基准上对照过** |
| S14 | **约束之间会互相干扰** | FeaXDrive：加可行驶区引导后曲率违规反而回升（0.13% → 0.88%）；普通 GRPO 分数更高但曲率违规高 2.4 倍 | **不能假设"多约束叠加一定更好"** |
| S15 | **分数与可行性不一致，且已被别人实测** | FA-GRPO 把曲率违规从 0.88% 抬到 **2.40%**（普通 GRPO **15.5%**），而 **ReCogDrive w/GRPO 的 PDMS 90.5 > FeaXDrive 的 90.0** | **直接用 PDMS 类指标做 RL 奖励会系统性破坏可行性**——这条把方向 A 的核心张力从"推测"变成"实测" |
| S16 | **"约束一致性训练/投影"仍只是论文主张** | FeaXDrive 的自适应曲率界、hinge-squared 惩罚、softplus SDF 引导**都在代码里逐条实现**；但**"约束一致性训练"在发布配置里权重为 0**，投影机制被标注弃用 | **引用时不能说"投影/一致性训练"**；但约束类方向**有可直接对照的实现** |
| S17 | **具身侧的加速路线已被走通** | DiffuserLite 粗到细 **122 Hz**（vs Diffuser 1.5 Hz），插件式提升 560% 而性能只降 3.2%；Consistency Policy **1–3 ms**（DDPM 110 ms） | 跨域迁移的"加速"部分**已有可借用的成熟做法**（方向 G） |

## 2b. 四篇 2024–2026 综述的收敛结论（**跨来源一致，可直接作为立项依据**）

| 收敛点 | S031（TITS 2025） | S032（2026） | S033（2026） | DP-S11/S15（CSUR 2026 / 2025） |
|---|---|---|---|---|

### 方向 A：约束注入的"层级选择"与实时化（**已完成全文核验，空白比初判小**）

- **依据**：P1 + P2 + 第 2b 节的四综述收敛结论（安全保证未解、实时性未解）。约束可以放在**四个位置**，各有代表：**去噪循环内**（PC-Diffuser，逐去噪步 CBF-QP，有证书，代价 5× 延迟 ≈ 2 fps）、**生成前结构层**（G2SD，图剪枝 + 短 bridge，代价是无多样性、仅小规模域）、**生成内软引导**（GuideFlow，CVF/CF/RFE，navhard **自报** 43.0 但 3.6 FPS；FeaXDrive，曲率违规 0.88% 但仍是软引导）、**生成之后否决**（DP-S11 §8.9 提出的规则式 "safety governor"，**仅有主张、无实现与实验**）。
- **重合风险（高）**：四个位置都已有论文或综述主张占据。**单纯"再加一个约束项"已不足以构成贡献**。
- **PC-Diffuser 的代码级补充（2026-09-23，见 [C003 §I](../code/traces/diffusion_planner_code_traces-2.md)）**：其 QP 是 **CasADi qpOASES 的加速度级 QP**（决策变量 `[a, a_nbr(10), slack(10)]`，`slack_weight=1e4`），**带 slack 且失败时回退到 nominal** → "认证级硬约束"**只在 QP 可行且活跃松弛为 0 时成立**；**每次规划要解 QP 的次数 = (H−1) × steps，数百量级**（"1.14 ms" 是**单次 QP** 口径）。→ 这条把"实时 + 硬约束"的障碍**从"选哪一层"改成了"能不能把 QP 次数从数百降到个位数"**——这是更硬、也更可测的门槛。
- **GuideFlow 的代码级补充（2026-09-23，见 [C003 §N](../code/traces/diffusion_planner_code_traces-2.md)）——这条把"约束注入"里最像"投影"的那一篇也打掉了**：GuideFlow 是**同基准 navhard 的"自报" SOTA（EPDMS 43.0；**⚠ 社区口径 27.1、且 43.0 不可从发布代码复现**，见 [sota-plan.md §1](sota-plan.md)）**，论文写 CVF 是"速度场向约束方向**投影**、λ=0.1、每步作用"。代码里：① **CVF 实为"朝 GTRS 专家轨迹的常数速度偏置"**（`v8:579` `zt + (v_pred + 0.11*limited_v_pred)*dt`，`limited_v_pred` 在**采样循环外**算一次），**全库无任何投影算子**；② **λ 是调参选出的 0.11**（注释 `# 0.05 ,0.08 ,0.15, 0.10, 0.12 , 0.11 best`），论文写 0.1；③ **"训练期能量项 RFE"在发布代码里不存在**——`transfuser_loss.py` 只有 4 项，v10 的 "rfe" 是**推理期 ESDF 条件 + CFG（scale 2.5）**；④ **`k_c=50` 只以死代码形式存在**（各版本 `self.num_inference_steps = 50` 从未被读取；三处 `flow_matching.py` 是 **11 字节占位文件**，全文 `# step = 50`）；⑤ **最要紧的一条：论文机制落在评测路径没 import 的版本里**——评测侧 import **`v6`**（且 `navsim_test/` 只发布到 v6），而 **CVF 只在 `v8`、RFE 只在 `v10`** → **按仓库给的评测脚本直接跑会命中"无 CVF、无 RFE"的版本，并撞上未定义的 `k_num`**。→ **结论：navhard 上"约束投影类"的最好成绩（43.0）目前不可从发布代码复现**，本项目若要以它为对照，必须先解决版本对齐。**"约束注入的层级选择"这个空白的实际大小，比论文叙述显示的要大。**
- **仍然空白的部分**（AI 判断，待验证）：
  1. **实时 + 硬约束同时满足**：PC-Diffuser 约 2 fps、GuideFlow 3.6 FPS，都远低于 10 Hz 需求；实时方案（45/59 FPS）没有硬约束。两者之间没有人做到。**代码级看，PC-Diffuser 的瓶颈很可能是 QP 调用次数（数百次/规划）而不是单次 QP 耗时**——这是一个可被直接攻击的点。
  2. **约束的层级对比**：PC-Diffuser（进去噪）与 G2SD（不进）在**同一基准**上的对照从未做过。
  3. **约束类型**：现有工作只覆盖碰撞/运动学/可行驶区，**没有交通规则、舒适性、他车反应式交互**；且 FeaXDrive 显示约束之间会互相干扰（P2b）。
  4. **基准迁移**：PC-Diffuser 只在 nuPlan（IDM 特权仿真）验证；NAVSIM 类相机端到端规划器上如何拿到几何约束所需的状态，没人回答。
- **最小验证实验**：在 NAVSIM v2 navhard（而非已饱和的 navtest）上，对同一 DiffusionDrive 类生成器，比较"约束进/不进生成过程"两种实现，报告 PDMS/EPDMS + **违规率**（**可直接采用 FeaXDrive 的判据，其代码已开源且已核验**）+ 延迟；同时记录与 PC-Diffuser 报告的 2 fps 的量级差。
- **需要**：NAVSIM v2 数据与 navhard 划分；能跑通基线推理的 GPU；CBF-QP 或投影算子实现；违规率判据（**FeaXDrive 已开源**：二项式核平滑 ksize=5 → 弧长参数化 → 变步长中心差分算 κ → 两端点补 0，违规率 = `(|κ|>bound).mean()`，且需说明用固定界还是自适应界）。
- **停止条件**：若约束注入使 EPDMS 下降超过 1 且延迟增加超过 3×（即在 PC-Diffuser 已报告的代价区间内没有改善），或无法把几何约束的状态输入在 NAVSIM 上合法获得，则停止。

### 方向 B：候选选择 / 评分器（P4）
- **依据**：DDV2 自述 selector 是薄弱环节；**DP-A34 给出更困难样本的构造方案**（摘要级：指出强规划器的候选集中在安全模式、**边界附近监督不足**；**⚠ 更正（第三十二轮）**：原写"横向推向可行驶边界、纵向推向领车"，该具体机制在论文表/来源索引里**查不到**——DP-A34 目前只有 `元数据 + 摘要` 级证据，故降级为摘要级可核表述）；EBench 指出单一成功率标量不足以诊断。**第二十四轮补上世界模型侧的三个代码级对照**（见 §2"选优依据"一条）：① **学到的奖励模型**（WM-24 WoTE，256 候选，PDMS 88.3/87.1，**18.7 ms**）；② **规则 cost volume**（WM-04 Drive-OccWorld，占据 → cost → `topk`）；③ **世界模型自身的损失**（WM-07 World4Drive，`重建+KL+余弦 → argmin`）。→ **"用什么信号选优"已有三种现成实现可对照**；且**三者都在选择环节依赖 GT**（OccWorld 的 GT 模式 / Drive-OccWorld 的训练用 GT 占据 / World4Drive 的 GT FDE）→ **"如何在推理期不依赖 GT 也能选对"仍是空白**。
- **反面对照（重要）**：**DP-A11 Flow Planner 是"纯生成、无选择"的最干净基线**（7 个 action token + 4 步 midpoint ODE → `average` 拼接 → 直取 `outputs[0,0]`，**全仓无任何选优代码**）。→ 做"生成 vs 选择"的对照实验时，**它是必需的对照组**；若"生成器 + 选优器"打不过"纯生成 + 无选优"，方向 B 直接不成立。
- **重合风险**：DP-A34 已做数据构造；DDV2 已做 mode selector（BCE + Margin-Rank）；**世界模型侧已有三种选优信号被实现**。
- **最小验证实验**：冻结生成器，仅训练评分器；对比"生成器自带候选池" vs "设计样本池"，看决策边界附近的选优是否变好；指标用 PDMS + 新定义的边界样本准确率。**⚠ 第四十一至四十三轮把"第一步"提前了一步**：**先纯推理量四项**（地板 / navhard 天花板 / 违规分布 / 池子 20→100 后再量天花板，见 [sota-plan.md §8.5](sota-plan.md)）——因为**"选优损失"现在是可测量**（`PDMS@1` = 池子天花板，DiffusionDrive 丢 **5.4**、DDV2 丢 **3.7**），**先量出损失有多大，再决定要不要训**；且**区分点必须落在"监督信号"（在线可得 vs 离线 GT 打分）上**（[§9.6](sota-plan.md)）。
- **需要**：冻结的生成器权重；NAVSIM 训练/验证划分；能构造扰动样本的脚本。
- **停止条件**：若评分器提升只出现在 Top-K 而非 Top-1，或提升幅度小于已有 selector 报告值，则降级为工程改进。

### 方向 C：训练-推理一致性（P5）
- **依据**：BridgeDrive 明确指出截断扩散不对称，并用扩散桥修正；UniTeD 用 anchor refresh；RoG-DAgger 用 DAgger 后训练。
- **重合风险**：BridgeDrive、UniTeD、RoG-DAgger 都在做，空间已被压缩。
- **最小验证实验**：同一 baseline 上比较"截断日程"与"桥式日程"在相同步数下的 PDMS 与多模态质量。
- **停止条件**：若桥式方案在同 backbone 下无稳定提升，则放弃该方向。

### 方向 D：多样性-质量的显式控制（P3）
- **依据**：DDV2 用 RL 提升 Top-K 质量但多样性下降（Div 42.3→30.3）；具身侧 FMER 用熵约束做可控探索。
- **重合风险**：DDV2、DIVER 都已在做；DIVER 还提出了 Div 指标。
- **最小验证实验**：把"多样性"从奖励项改为可控条件（例如给定多样性预算），检验 PDMS-多样性曲线是否比奖励加权更平滑。
- **停止条件**：若曲线与现有奖励加权无显著差别，则放弃。

### 方向 E：表示层（P7 + 输出接口）
- **依据**：FeaXDrive 主张轨迹中心式而非噪声中心式；MeanFuser 用连续高斯混合噪声替代离散词表；WAM-Flow 用离散 token 空间；DP-A15 直接输出控制量。**第二十四轮补上"世界模型 → 规划器"的接口清单**（见 §2）：**五条 + 第 6 条**（token 级联合自回归 / 隐状态级条件 / 特征级条件 / 选优依据 / RL 的 reward-next-state / **动作专家内嵌**），且**路线 1–4 的规划器本身都不是生成式**。→ **"表示层"的选择空间现在有了完整坐标系**：表示（轨迹 / 控制量 / 离散 token / 隐变量）× 接口（六条）。
- **重合风险（已显著上升）**：这几条已被分别占据；**更关键的是 WM-11 DriveLaW（CVPR'26）已把"世界模型 + 扩散规划器"两种接法都实现过**（动作专家内嵌 + 隐状态外挂）→ **"把未来表示接进扩散规划器"这个动作本身已不新颖**；剩余空间更可能在 **"输出接口（轨迹 → 控制量）× 可行性表示"的结合**，以及 **"收益来源拆解"**（未来信息是"条件"还是"训练信号"）。
- **最小验证实验**：在同一生成器上替换输出表示（轨迹 vs 加速度/曲率），比较可行性指标（运动学可行率）与 PDMS。
- **停止条件**：若可行性提升不体现在可测指标上，则放弃。

### 方向 F：评价协议（P8，**已被 2026 年综述单列为开放问题**）
- **依据**：S032 **§IV.D 把"如何评估生成式规划"单列为开放问题**（分布只有能把安全、目标一致的轨迹排在前面才有用）；§VII.C 指出跨协议排名反转、子指标饱和、NAVSIM 只是代理证据、**建议不设单一 best method**；S033 §7.3 指出基准饱和与推理成本漏报；DP-S15 指出多数生成式规划器只优化开环、闭环下常输给更简单方法；DP-A25 已示范"同一扩散模型兼做规划器与安全关键场景生成器"。
- **重合风险（高）**：评价问题已被多篇 2026 综述点名，属于"公认开放问题"，但**提出批评容易、给出被采用的协议难**；若只写一篇"批评现有指标"的论文，贡献不足。
- **最小验证实验**：用同一模型生成"边界场景"，检验现有 PDMS/EPDMS 能否区分两类不同失效模式（例如"保守但安全"与"激进且违规"）；若能区分，说明不需要新指标。
- **停止条件**：若现有指标已能区分主要失效模式，则这只是论文中的一小节而非独立方向。

### 方向 G：跨域迁移（具身 → 驾驶）
- **依据**：第 4 节机制表；DP-E16/DP-E14 显示"冻结骨干 + 条件适配"可省算力。
- **重合风险（已显著上升）**：BridgeDrive、AnchDrive 等已在借用机器人扩散策略的机制（锚点、桥）；**更关键的是"具身 VLA 的 action expert 已经进到驾驶的视频扩散 transformer 里"**——**WM-11 DriveLaW 的 `action_expert: true` 与 π0 的 action expert 同构**（工作空间已有 π0 官方代码核验，见 [transfer.md §1.4](../topics/diffusion-planner/transfer.md)）；VLA 侧的 **DriveMoE 底座就是 π0**（见 [vla/verification.md §4.3](../topics/vla/verification.md)）。→ **"能不能搬"这个问题已被回答为"已经有人在搬"**，本项目的问题应改成"**搬到哪一层、以及搬过来的收益能否被拆解**"。
- **最小验证实验**：把 action chunk + 一致性蒸馏组合到驾驶规划器上，测延迟-性能-多样性三角。
- **停止条件**：若迁移机制带来的收益与已有少步化方案重叠，则仅作为工程手段。

### 6.2 固定规则

- **基准与划分**：NAVSIM v1 navtest（PDMS）、v2 navtest（EPDMS）、v2 navhard（EPDMS）是三套不同口径，禁止混用；Bench2Drive/CARLA 是闭环反应式，nuPlan 是另一套闭环协议。**代码级补充（第二十轮，见 [benchmarks.md §2.1](../direction/benchmarks.md)）**：devkit 配置名是 **`navhard_two_stage`**（"navhard" 只是官方 HF 榜的简称），且三套 split 的 **`num_future_frames` 不一致**（`navtest`/`navtrain` 10、`navtest_two_stage` 16、`navhard_two_stage` 8），困难划分还带 `include_synthetic_scenes: true` → **"同一份数据换个划分"不成立**。另注：v2 两阶段**默认用反应式 IDM 交通**（v1 才是 `non_reactive`）。
- **输入权限**：纯相机 / 相机+LiDAR / 矢量化特权输入 / 额外先验（锚点、goal、VLM、未来潜状态）必须分别标注；backbone 不同时 PDMS 不可横比。**代码级补充（第十八轮，见 [C005 §I](../code/traces/e2e_trunk_code_traces.md)）：标注必须按数据管线实测字段做，不能按配置文件 flag 做**——`use_external` 这个 flag **两个方向都错**（UniAD 声明 `True` 却全仓未消费；SparseDrive 声明 `False` 却实际消费 CAN bus 的 `ego_status`）。另实测：**TCP 与 ST-P3 都是纯相机**（TCP 的 LiDAR 行在 `base_agent.py:170` 被整段注释），"相机+LiDAR"这一类实际只有 **TransFuser**（`sensor.lidar.ray_cast`）与 NAVSIM 系的 DiffusionDrive / GoalFlow / MeanFuser（配置里有 `lidar_seq_len` + `lidar_architecture`，即吃 LiDAR）。
- **主干对齐清单（代码级）**：不能只说"都用 TransFuser"，必须逐项对齐 **`tf_d_model`**（DD/V2 256、MeanFuser **128**、GoalFlow **512**）、**`lidar_seq_len`**（DD/V2/GoalFlow 1、MeanFuser **4**）、**输出轨迹点数与采样间隔**（NAVSIM 系统一 8 点 / 4 s @0.5 s）。见 [C003 §F](../code/traces/diffusion_planner_code_traces.md)。
- **输出模态与选优方式必须标注**：**第二十四轮从三类扩到五类**——① 单模回归（UniAD / VAD v1 / TransFuser / NEAT）② 锚点+回归（SparseDrive）③ 离散词表+分类（VADv2 / Hydra-MDP）④ **采样+规则代价选优**（**ST-P3**，2400/1800 条候选 + 7 项代价 + `topk`）⑤ **按命令切分支**（LBC / CIL）。"生成 → 选择"的最后一步还要区分 **选优** 与 **均值化**（GoalFlow 属后者）。见 [C005 §G](../code/traces/e2e_trunk_code_traces.md)（三类→五类的分类）与 [C005 第二册 §K](../code/traces/e2e_trunk_code_traces-2.md)（CARLA 系 6 个仓库的规划/控制输出）。**特别提示**：**④ 与 DiffusionDrive 的"扩散 + scorer 选优"结构最接近，是最容易被误标成"生成式"的一类**；且 **ST-P3（ECCV'22）的 `costvolume` 就是模型输出的一路** → **"用世界模型输出选优"不是新机制**。
- **"命令"这一维也要标注**（第二十四轮，见 [C005 第二册 §K](../code/traces/e2e_trunk_code_traces-2.md)）：13 个主干仓库对命令有**三种处理方式**——**显式输入**（TCP / VAD / VADv2 / SparseDrive / UniAD）、**算了不用**（**TransFuser 与 NEAT 都算了 `next_command` 却从未传给模型**）、**只用 `target_point`**。→ **"用了命令"不成立为统一事实**，跨方法比较时必须逐个确认。
- **跨基准禁止直比**：nuScenes 系（UniAD / SparseDrive / VADv2）的规划视野是 **3 s / 6 步 @2 Hz**，NAVSIM 系是 **4.0 s / 8 poses**，两者本来就不该放在同一列里。**且 nuScenes 系内部也不可比**（第二十四轮，见 [benchmarks.md §2.8](../direction/benchmarks.md)）：**"L2/碰撞"在 UniAD / VAD / VADv2 / SparseDrive 里是四套不同实现**，UniAD 自己的代码里还有 `uniad` / `stp3` 两套 L2 定义（**单步值 vs 前缀累积平均**；`stp3` 是前缀累积平均、`uniad` 是单步值，见 [benchmarks.md §2.8.2](../direction/benchmarks.md)）→ **本项目不以 nuScenes 开环作主表**。
- **同条件比较**：优先"同一基线、同一数据、同一评测"的受控改动；跨系统整体比较只能作为参考。**建议自己复现基线**，不直接引用他人表格（GoalFlow 的例子说明差异可达 4.6 分）。**判据（第七十三轮补）：何谓"同一基线"以代码血统为准——S1/S2 指向同一代码库者（如 VADv2←VAD、GenAD←VAD、DIVER←SparseDrive）分差才可归因到机制，跨库者不可横比；继承事实源见 [E2E 主干 §继承关系](../direction/lineage.md) 与 [扩散规划器 §继承关系](../topics/diffusion-planner/lineage.md)**。
- **"从生成输出反推的轨迹指标"不可复用**（第二十五轮补上论文侧原文，见 [world-model/papers.md §4.5](../topics/world-model/papers.md)）：**WM-20 DrivingGen（ICLR'26）是唯一的生成式视频世界模型基准**，其 **ADE / DTW 是从生成视频用 PnP + UniDepthV2 的 SLAM 管线反推**的。论文**自己承认两处**——§4.1 称误差可源于生成视频伪影 "impair SLAM-based trajectory recovery"；**B.9 称轨迹类指标与人类一致性最差**（"noisy monocular SLAM and metric-depth recovery … with artifacts"）；**B.2 还对 SLAM 失败帧做常速外推 + 随机抖动**（**使 ADE 15.18 → 16.84**）→ **ADE 数值受管线选择支配**（不同 SLAM 管线差 1–2 m）。**更关键的是 §6 原文明确"当前全为 open-loop"、"no standardized closed-loop framework exists yet"、"infeasible at this stage"** → **它不评规划有效性**。→ **本项目若要评生成式规划器：不能复用其轨迹指标；可复用的只有它的"分布 / 质量 / 时序一致性"三类框架与 FTD（把轨迹分布做成 Fréchet 距离）这个做法**。**另一侧的证据（第二十四轮）**：**WM-20 的代码核验也显示全仓无 planner-in-the-loop 接口**（grep `planner｜pdm_score｜navsim` 零命中）。→ **"评价协议"（方向 F）的空白因此被双重确认：既没有现成工具，也没有现成口径**。
