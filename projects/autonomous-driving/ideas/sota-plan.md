## 2. 四条关键结论

1. **"榜上 SOTA ≠ 可复现 SOTA"**——第一名 **55.5 无代码**；第二名 **54.6（DrivoR）也无代码**（只承诺"will be made available"）；**GuideFlow 自报 43.0 与社区口径 27.1 差 15.9 分且不可复现**。→ **navhard 前二都拿不到代码，这个基准的"头部"目前是空的。** **⚠ 第六十九轮更正**：**TOAD 的 NAVSIM-v2 结果已核实就是 navhard**（论文 §4.1 原文 "navhard-two-stage split"）→ **论文口径下榜一由 55.5（DriveFuture）变为 56.3（TOAD + DrivoR）**。**⚠⚠ 第七十轮再更正两处**：① **TOAD 与 DrivoR 的代码其实都已发布**（[valeoai/TOAD](https://github.com/valeoai/TOAD) 25★、[valeoai/DrivoR](https://github.com/valeoai/DrivoR) 280★，`created` 分别为 2026-08-27 / **2026-01-05**）——第六十九轮写的"TOAD 代码未发布"**是错的**（依据只有摘要那句 "will be made publicly available"）；② **换到官方公开榜口径后，"头部拿不到代码"更强**：官方榜**前 9 名里只有第 7 名 DriveZero 有实仓**（前 6 名中 4 名匿名、第 2 名对应的仓是占位仓、第 3 名只有项目页）→ **结论方向不变、依据更硬**（见 [§1.0](sota-plan.md)）。
2. **scorer（选优器）的量级远大于机制**——DriveFuture 同文受控消融**不含 scorer 只有 34.6，含 scorer 是 55.5** → **scorer ≈ +20**，而"加未来条件"这类机制只有 **+3.7**。→ **提分的最高杠杆不在"再加一轴机制"，而在"把选优这一环做好"**（这条修正了 `preparation.md` §5 原来的横切读法）。**⚠ 第四十一轮补**：这个 **+20 有三个成立条件**（基线**无**选择环节 / 候选池 **100 条** / 同文受控，见 [§7.2](sota-plan.md)）——**起点 DiffusionDrive 只有 20 锚点，拿不到它**（[§8.2](sota-plan.md)）→ **B 的目标与第一步已据此改写**（[§8.4](sota-plan.md)、[§8.5](sota-plan.md)）。
3. **navhard 的分数被乘性违规项支配**——PDMS/EPDMS 的 NC 是 **0/1 乘性项**（一次碰撞即把该帧乘 0），navhard 全是困难场景 → **降违规的边际收益是非线性的**，与 navtest"挤在 88–91"完全不同。
4. **我们的"小同行"比想象的小得多**——13 行里 **DrivoR / ZTRS / DriveSuprim 都是选择/评分式（非生成式）**，GTRS-E 是半生成，**只有 DriveFuture 与 DiffVLA 是纯生成式规划器**。→ **"小方向 SOTA"的分母很小**，这是"退而求其次"那条路的直接依据。**⚠ 第三十六轮更正**：DiffVLA 的**发布代码已把扩散头换成 EPDM 打分头**（§7.6）→ 按"**发布代码**"这个口径，**纯生成式规划器只剩 DriveFuture 一个，而它无代码**。→ **"有代码的纯扩散规划器"这个子榜在发布代码层面是空的**（DIVER 43.4 的代码跑不通、DiffVLA 45.0 的头被换掉）。

### 5.2 路线 ①（主推）：**"复现 + 拆解" navhard 榜首**

- **做法**：把 DriveFuture 那套（**未来潜状态条件** + **100 条候选** + **scorer 选优**）实现成**可复现**版本，再叠合规/约束项。

### 5.3 路线 ②（成本最低，可先跑）：**只做选优器**

### 5.4 路线 ③（**新发现的捷径**）：**套用 SimScale 的 co-training 框架**

- **✅ 前置已于第三十七轮解决（见 §7.7.3）**：① 原来写"+8.6 是它对某个基线的报告值，**对更强基线是否同样有效未知**"——**已核：成立，且不衰减**（四条基线增益 **+5.1 / +5.8 / +6.1 / +8.6**，最强的那条拿到最大增益）；② **SimScale 已经测过 DiffusionDrive**，仓库里就有 `diffusiondrive_agent.yaml` + **HF 上发布好的 `diffusiondrive_sim_navhard.ckpt`** → **路线 ② 与路线 ③ 可以在同一个起点上直接串起来，且第一步只需推理**。

- **判定**：**作为增益工具而不是创新点**——它能把上面几层目标的达成概率显著抬高。

### 7.3 据此修正路线 ②（§5.3）

原表述的推法是"若 scorer 的 +20 量级可复现，单这一步就能过 45.0 甚至 49.4"。**这个推法不成立**：

- **DIVER 43.4 / DiffVLA 45.0 是"提交给榜单的最终配置"**——其分数里**是否已含一个选择环节，工作空间里没有记录**（DIVER 产出 6 条候选，评测时必须选一条）→ **在这些数上再叠 +20 是重复计数**；

**修正后的路线 ② 第一步**：先量出候选基线的「**无选择地板**」——同一份权重下，"取第 0 条候选"或"随机候选"在 navhard 上的分数。**真正的提分空间 = 最终分 − 地板**。这一步**只需推理、不需训练**，是整条路线上最便宜的一次实验。

#### 7.6.1 DiffVLA 为什么不能当起点（本轮从发布代码取到的证据）

`boschresearch/DiffVLA`：**36★ / Apache-2.0 / 44 MB / 最后推送 2025-12-08**（⚠ `DiffVLA/DiffVLA` 是**空壳**，0 KB）。

1. **README §5 自述**：「The released version has some modifications compared to the paper on arXiv: 1. The trajectory head has been updated from **Diffusion Drive** to a self-developed **Transformer-based Trajectory Head**. 2. A **reward loss** derived from multiple EPDM sub-metrics has been introduced.」
2. **代码级**：`navsim/agents/diffvla/` 下**活跃头是 `trajectory_head_reward.py`**（目录里**没有任何扩散轨迹头文件**）；`modules/` 只剩 `conditional_unet1d.py` 与 `scheduler.py` 两件扩散残件；`diffvla_config.py` 里 `diff_loss_weight = 20.0` 仍在，但**不被活跃头使用**。
3. **它其实是一个"选优器"**：`RewardHead` 按 **nc / dac / ddc / tlc / ep / tc / lk / hc 八个 EPDM 子指标**各出一个头，损失是 **BCE against 离线 GT 标签**（`compute_reward_loss`，监督来自 `pdm_scores_8192`，由仓库脚本 `navsim/misc/gen_multi_trajs_pdm_score_ours.py` 生成）；**推理期**用 `combined_score = w1·cls + w2·nc + w3·dac + w4·(5tc + 2lk) + w5·ddc`（**`w = [1.0, 4.0, 1.2, 0.02, 8.0]`，手调常数**）**argmax 选一条**。→ **`ep` 与 `hc` 算了但没进最终分**（与 EPDM 的定义不符）。
4. **配置与论文不一致**：`num_voc = 8192`（论文写 **N_anchor = 32**）。

→ **两条推论**：

- **对 §1 / §3 / §5.1 的更正**：「有代码的**纯扩散**规划器 SOTA = **45.0**（DiffVLA）」**站不住**——45.0 是**论文里带扩散头的竞赛成绩**，而**发布代码的头不是扩散头**，且该版本**仓库未报告任何分数**。→ **"有代码的纯扩散规划器"这个子榜，在"发布代码"这个口径下是空的**（DIVER 43.4 代码跑不通、DiffVLA 45.0 头被换掉）。这是[七类"名字≠实际"陷阱](../judgments.md)的一个**新形态**：不是"配置关掉了机制"，也不是"机制落在评测没 import 的版本里"，而是**发布代码里根本没有论文那个机制**。
- **对方向 B（选优器）的增益**：发布版 DiffVLA 是**"离线 GT 打分监督的选择器"的第 4 个代码级实例**（前三个：WoTE 的 PDM 子指标 / Drive-OccWorld 的 GT 占据 / World4Drive 的 GT FDE），而且它**有代码、可运行、候选池 8192（比 DriveFuture 的 100 还大）** → **它是方向 B 最合适的载体**（把"离线 GT EPDM 监督"换成在线信号），**而不是路线 ② 的生成器**。这条把 §5.3 的"自圆其说"从"三种实例"抬到**四种**。

#### 7.6.2 起点选定后的第一个坑：候选池只有 20 条

§7.2 条件② 说"**上限由候选池决定**"。DiffusionDrive 只有 **20** 条候选（vs DriveFuture 的 **100**、DiffVLA 发布版的 **8192**）→ **从 24.2 出发不要指望 +20.9**。

→ **正确的顺序是"先把候选池做大，再做选优"**：这正好落在 §7.4 表里**"生成机制"与"选优"两轴的组合**上（两条轴**不能相加**，因为选优的上限被生成器的候选池封住）。**这也解释了为什么 §7.3 那一步（先量无选择地板）必须先做**——只有先知道"第 0 条候选值多少"，才知道后面的提分是来自"生成得更好"还是"选得更好"。

## 8. 算力约束下的重排（2026-09-24 第四十一轮新增）

**动因**：用户给出了**实际算力**与**最终目的**——**自备双卡 RTX 3090（2×24 GB = 48 GB）做实验，出成果后可租到 A800 80G（单卡）**；且「**最核心目标是发一篇 CCF-A，SOTA 是手段不是目的**（"只要能实现这个目标，其他都可以妥协"）」。这两条**同时**改变了 §4 的排序依据，所以重算一遍。

### 8.1 算力账：哪些轴被直接排除

| 轴 / 路线 | 代表工作的**实际训练规模** | 48 GB 下 |
|---|---|---|
| **VLA** | ReCogDrive 2.3M 数据 + 7B 级 VLM | ❌ 排除 |
| **世界模型（视频扩散）** | 视频扩散预训练 | ❌ 排除 |
| **路线 ①「复现 DriveFuture」** | 原文自述 **8×NVIDIA 5090 / 100 epochs**（≈12–16× 3090） | ❌ 排除（A800 单卡也补不上） |
| **NAVSIM 评测本身** | devkit 是 2D 伪仿真、无渲染 | ✅ **很便宜** |
| **60M 级 TransFuser 规划器（DiffusionDrive 档）** | 60M 参数 / ResNet-34 | ✅ **可训** |
| **选优器 / 约束层等小模块** | 参数少 | ✅ **便宜** |

→ **能做的只剩"冻结 + 小规模训练 + 推理期"这一类。**

### 8.2 §4 的排序依据要改：那个 **+20 拿不到**

§4 把「B 选优器」排第一，**唯一依据是 `scorer ≈ +20`**。但第 35–37 轮已证明：那个 +20 是 **DriveFuture 自己 100 候选池**上的受控值（34.6 → 55.5），且**不能叠在"已含选择环节"的方法上**。而 §8.1 说明**我们训得起的生成器是 DiffusionDrive 档（20 锚点）** → **+20 不可达**。

### 8.3 但 B 有一个**已发表的、量级更小却更可靠**的证据：**选优损失**

第四十一轮把 DDV2 的 Table 3 **核到原文**（此前只抄了数字、没钉死语义）：

| 方法（均 20 条候选） | 原始池天花板 `PDMS@1` | 其选优模块的输出 | **选优损失** |
|---|---|---|---|
| **DiffusionDrive** | **93.5** | **88.1** | **−5.4** |
| **DiffusionDriveV2** | **94.9** | **91.2** | **−3.7** |

**口径（原文）**：题注 "PDMS@K denotes the PDMS score evaluated on the Top-K ranked trajectories"，正文 "the models' **raw outputs, evaluated before their respective selection modules**"，并把 @1 称 upper bound、@10 称 lower bound → **`PDMS@1` 就是池子里最好那条**。
**动机可引原文**：DDV2 自己写道 "**this over-reliance is a critical concern**, as selector modules typically have fewer parameters, leading to weaker generalization capabilities. Consequently, **they are prone to failure in out-of-distribution scenarios**"。

→ **这是方向 B 最强的一条证据**，三个优点：① 来自**已发表的同基准数字**（不是推测）；② **在 2×3090 上完全可复现**（冻结 60M 模型 + 训一个头）；③ **动机可直接引用原文**。

### 8.4 重排后的判断（**AI 判断，未验证**）与 **B 的目标改写**

| 排序 | 方向 | 48 GB 下 | 说明 |
|---|---|---|---|
| **1** | **B 选优器**（**目标改写**） | ✅ **唯一能立刻产生真实分数的方向** | 依据换成"**选优损失**"（§8.3），不是 +20 |
| 2 | A 约束 + 实时 | ✅ 成本低 | 两个真空位；上限取决于违规项剩余空间 |
| 3 | F 评价协议 | ✅ 几乎不耗算力 | 第 37–39 轮的审计结论可当主贡献或动机 |
| ❌ | ① 复现 DriveFuture / VLA / 世界模型 | ❌ | 算力不足 |

**⚠ 本节最要紧的一句——B 的目标要从"打败 48.0"改成"压缩选优损失"**：

- **不是**"我们的总分超过某个别人的数"——那依赖别人放不放代码、用哪套口径（§7.7.1 已证明三张表互差 3.3–5.2）
- **而是**"**我们把选优损失从 5.4 压到 X**"——**天花板是可测的**（DDV2 已示范怎么测）、**不依赖别人放代码**、**且是可复现的**
- 并且 **navhard 是 OOD 场景**，按 DDV2 自述的 hazard，那里的损失**应当更大** → **这正是论文的主结果**

### 8.5 第一步（纯推理，2×3090 足够）

1. 跑通一个已发布 ckpt（**SimScale 的 `diffusiondrive_sim_navhard.ckpt`，navhard 32.6**——它是**已发布的最强扩散规划器**）→ 拿到我们自己的可信基线，同时验证本地 devkit 口径
2. **量 navhard 上的池子天花板**（`PDMS@1` 的 navhard 版）—— **这一步是全新的：DDV2 只做了 navtest**
3. 量 floor（固定取第 0 条候选）与 top-1 的违规项分布
4. **把池子从 20 放大到 100**（多重采样噪声，纯推理）**再量一次天花板**——这一个数同时回答"池子值多少"与"选优值多少"（第四十二轮补，见 §9.4）

→ **天花板 − 基线 = B 的全部空间。** 若 navhard 上这个差显著大于 navtest 的 5.4，**B 成立**；若几乎不涨（池子被 20 个锚点锁死），**转 A**，且评测脚手架已搭好、不浪费。

⚠ **实际前置**：上述权重与数据**全在 HuggingFace**——沙箱不走代理时不可达（走 `127.0.0.1:7897` 可达，第五十五轮实测）；checkpoint 已定位（[rounds-56.md](../history/rounds-56.md) §二）。

## 9. 选优损失账本（2026-09-24 第四十二轮新增）

**动因**：§8.4 把方向 B 的目标改成了"**压缩选优损失**"。那么这个量**到底有多少已发表的实测值**就必须盘清——它既是论文的动机节，也是第一步实验的设计依据。

**⚠ 盘完发现一个此前没人分开过的区别：已发表的数字分属两个不同的量。**

| 量 | 定义 | 衡量什么 | 已有实测 |
|---|---|---|---|
| **天花板 gap** | **池子里最好那条 − 模型实际选的** | **选优器本身有多差** | **只在 navtest 上有 3 个** |
| **地板 gap** | **有选优 − 完全不选**（取固定第 0 条） | **选优这一环整体值多少** | **只在 navhard 上有 2 个** |

### 9.1 天花板 gap（navtest，3 个实例）

| 方法 | 池子 | 天花板 | 选中 | **gap** | 来源 |
|---|---|---|---|---|---|
| **DiffusionDrive** | 20 | **93.5** | **88.1** | **5.4** | DDV2 Table 3（第四十一轮核到语义，见 §8.3） |
| **DiffusionDriveV2** | 20 | **94.9** | **91.2** | **3.7** | 同上 |
| **ExploreVLA** | **6** | **93.7**（best-of-N） | **90.4**（无 best-of-N） | **3.3** | [VLA-18 表](../topics/vla/verification.md)（**其 best-of-N 的判据未核到细节**，不一定是 oracle） |

口径：全部 **NAVSIM v1 navtest PDMS**。

### 9.2 地板 gap（navhard，2 个实例）

| 方法 | 池子 | 无选优 | 有选优 | **gap** | 来源 |
|---|---|---|---|---|---|
| **DriveFuture** | **100** | **34.6**（同文受控消融"不含 scorer"） | **55.5** | **20.9** | DriveFuture Table 4 → Table 1 |
| **GuideFlow** | **100** | **27.1**（no-scorer 变体；代码里默认取 `proposals[0]`） | **43.0**（⚠ **不可复现**，见 [C003 §N](../code/traces/diffusion_planner_code_traces-2.md)） | **15.9** | GuideFlow Table 1 |

口径：**navhard EPDMS**；且**两篇分属修复前 / 后两套实现**（§7.7.5）→ **只能各自内部比，不能横向合看**。

### 9.3 这个区别为什么重要（**本节最要紧的一条**）

记 `F` = 地板、`S` = 选中、`C` = 天花板，则 **F ≤ S ≤ C**，且

- **地板 gap = S − F**（已测：navhard 上 **11.1 / 15.9 / 20.9**——三个实例，见 §9.2 与 §9.6）
- **天花板 gap = C − S**（已测：navtest 上 **3.3–5.4**）
- **总空间 = C − F = (S−F) + (C−S)**

→ **两条推论**：

1. **navhard 的"选优总空间"有一个已发表的下界**：**`C − F ≥ S − F = 11.1–20.9`**（三个实例，其中 GTRS 的 **+11.1 完全可复现**——§9.6）。**这是本项目目前对"提分空间"最硬的一个数**，而且**不依赖天花板测量**。
2. **但"天花板 gap"在 navhard 上从未被任何论文报告**——而它才是"**选优器本身还剩多少可改进**"的直接度量。→ 这正是 §8.5 第一步要测的东西，**现在它的必要性有了定量理由**：navtest 的 3.3–5.4 说明这个量**确实存在且可测**；navhard 难度更高，按 DDV2 自述的 OOD hazard **应当更大**——**但这是假设，必须测**。

### 9.4 对我们的口径意味着什么（**一处必须收窄的外推**）

**地板 gap 的三个实例**（§9.2 两个 + §9.6 一个）**都是 100 候选池**，而**我们能冻结的生成器是 20 锚点**（§8.1）→ **不能把 11.1–20.9 直接外推到 20 锚点池**。

但反过来，这个对比**强化了 §7.2 条件②**（"上限由候选池决定"）：

> **池子越大，选优空间越大** → **"先扩大池子"与"做好选优"是同一件事的两面**，不是两条独立路线。

→ 因此第一步（§8.5）除天花板外**还要顺带量一个数**：把池子从 **20 放大到 100**（多重采样噪声，纯推理）后**天花板涨多少**。这一个数同时回答"池子值多少"与"选优值多少"。

### 9.5 账本的空白（**明确列出，避免以后重复找**）

> **⚠ 第四十三轮更正**：本节原列的 5 项里，**第 3 项是错的**（GTRS Table 1 就有一张"池子大小 + 地板"表，见 §9.6），**第 1 项也部分被填**（§9.6 给出第三个 navhard 地板 gap）。**"无人报告"本身就是一个断言，必须举证**——本轮为此在四篇本地论文全文里逐篇搜过。

- **navhard 的天花板 gap**（`C − S`）：**仍无人报告** ← **我们要测的**（§9.6 只填了地板，没填天花板）
- **navtest 的地板 gap**：无人报告（DDV2 只给了天花板）
- ~~**"池子大小 → 天花板"的曲线**：无人报告~~ → **❌ 已推翻（第四十三轮）**：GTRS Table 1 有**"池子大小/组成 → 分数"的曲线**（100 → 16,484），只是它是"**选中分**"的曲线而非"天花板"曲线；**且它不单调**（8,292 > 16,484）。详见 §9.6
- **池子 ≥ 100 的扩散规划器的天花板**：无人报告（DDV2 / DD 都是 20；GTRS 是评分式、非扩散）
- **20 锚点模型在 navhard 上的 `proposals[0]` 分数**：无人报告（GuideFlow 的 27.1 与 GTRS 的 25.6 都是 100 候选池的）

### 9.6 第四十三轮补：GTRS Table 1 填掉两处"空白"，并给出一条**反向**证据

§9.5 说"池子大小 → 分数"的曲线无人报告。**这个断言是错的**——GTRS 的 **Table 1** 就是一张完整的"**词表 / 池子 + 地板**"表（论文原文逐字核验），而且它来自**可复现的那一侧**（GTRS 有 4 个已发布 ckpt）。

**GTRS Table 1**（navhard；`Vdp` = **100 条动态候选**，`V_XL` = **16,384** 静态词表，`V_L` = **8,192**）：

| 方法 | 训练词表 | **推理池** | EPDMS1（真实） | EPDMS2（合成） | **EPDMS** |
|---|---|---|---|---|---|
| **DP w/o Scorer** | — | **Vdp（随机取）** | 60.9 | 40.8 | **25.6** ← **地板** |
| GTRS-Dense | V_XL | **Vdp**（100） | 76.6 | 48.6 | **36.7** |
| GTRS-Dense | V_XL | V_XL（16,384） | 78.1 | 50.2 | 39.7 |
| GTRS-Dense | V_XL | Vdp ∪ V_XL（16,484） | 77.4 | 52.7 | 40.8 |
| GTRS-Dense | V_XL | **Vdp ∪ V_L（8,292）** | 71.8 | **57.3** | 42.0 |
| GTRS-Dense | V_XL（+dropout） | Vdp ∪ V_L | 73.1 | **59.0** | **43.4** |

**① 第三个 navhard 地板 gap，而且在可复现侧**：**25.6 → 36.7 = +11.1**，**GTRS 自己在正文写了这个数**（"outperforming the generator with random selection substantially (**+11.1 EPDMS**)"）。→ 加上 §9.2 的两个（20.9 / 15.9，**都不可复现或口径混装**），**地板 gap 现有三个实例，其中只有 GTRS 这个完全落在可复现侧**。**且三者都是 100 候选池** → §9.4 的收窄结论不变，反而更硬。

**② "池子大小 → 分数"的曲线存在，而且它不单调**：从 100 → 16,484 条候选，
- Vdp（100，随机）**25.6** → Vdp（100，评分）**36.7** → V_XL（16,384）**39.7** → Vdp ∪ V_XL（16,484）**40.8**
- **但 Vdp ∪ V_L（8,292）反而 42.0 > Vdp ∪ V_XL（16,484）的 40.8**
→ **GTRS 自己给了原因**："likely because the **reduced vocabulary complexity leads to better generalization in out-of-domain synthetic data**"。→ **"先把池子做大"不是免费的**：池子必须与评分器匹配。

**③ 这条曲线里藏着一个内建的 OOD 对照，而结论是"有得有失"**：EPDMS1 = Stage 1（真实数据）、EPDMS2 = Stage 2（合成数据，即 OOD）。以"评分器是否泛化到未见词表"为自变量、训练配置相同：
- **EPDMS1：71.8（Vdp∪V_L）vs 77.4（Vdp∪V_XL）→ −5.6（变差）**
- **EPDMS2：57.3 vs 52.7 → +4.6（变好）**
→ **"面向泛化的评分"用 Stage 1 换 Stage 2**，不是干净的净胜。**⚠ 这是对"选优在 OOD 上更值钱"的一个反向证据**——选优在 OOD 上确实更有效，但**代价是同分布侧下降**；而 EPDMS 的两阶段聚合把这笔交易**部分藏进了总分**（与 §7.7.5 的"乘性项主导"同向）。

**④ 对方向 B 的一条新颖性警示**：GTRS 的**主贡献之一就是"让评分器在未见过的词表上工作"**（训练 16,384、推理 8,192 + vocabulary dropout）→ **"先把池子做大、再让选优器泛化"这一块已被部分占据**。→ **我们的区分点必须落在"监督信号"（在线可得 vs 离线 GT 打分）上，而不是"池子"上。** 这与 §8.4 的改写一致，但**现在有了必须避开的近邻工作**。

**⑤ 又一个被算力排除的规模**：GTRS 训练用 **24× A100**（§4.2 原文）→ 与 §8.1 的结论一致。

### 9.7 第六十八轮补：**"做选优"已被他人占住，且有强对手**（2026-09-30）

|---|---|---|
